# Guardian: Detecting Robotic Planning and Execution Errors with Vision-Language Models

## What this paper does
Guardian builds GuardianFail-36k by procedurally perturbing successful trajectories (RLBench sub-task action perturbations; for real BridgeDataV2 data, perturbing only the paired subtask text or replacing the end image with the start image) and adding VLM-written reasoning traces, then LoRA-fine-tunes InternVL3-8B (frozen vision encoder, each view encoded separately) to answer with CoT whether a plan is valid and whether a subtask succeeded from pre/post multi-view images. It is inserted into 3D-LOTUS++ as a per-step verifier with up to 3 retries.

## Goal-by-goal answers
### Goal: What mechanism does it use for step-level success judgement?
Binary VQA VLM_exec(I_start, I_end, T, P_i) → {0,1}, CoT before the answer [full text, Sec 4.1 Eq 2, Sec 4.2–4.3]. The verifier receives a fixed pair of pre/post images; it does not choose views or request additional evidence [Sec 4.1, 4.4].

### Goal: Where do its failure examples come from?
"Starting from successful demonstrations, we procedurally perturb task plans and subtask executions" [Sec 1]. Real-robot failures "must be derived from already-collected successful demonstrations": they "preserve the recorded trajectory unaltered and perturb only its paired subtask text instruction", plus "Revert action — ... replace the end image with the start one" [Sec 3.2].

### Goal: What errors and downstream effects does it report?
Execution: correctly identifies 91% of successes and 76% of failures; missed failures concentrate in "wrong object state or placement (61%)", where "the action completes, but a wrong final pose betrays the failure, which requires more spatial reasoning" [App B]. Off-the-shelf InternVL3-8B as verifier "performs poor distinction between success and failure, which damages the base robot policy performance in nominal cases" [Sec 5.6, Table 7]. RLBench downstream 0.45→0.54 with Guardian [Sec 5.6].
