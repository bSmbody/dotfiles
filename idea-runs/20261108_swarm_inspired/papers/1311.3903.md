# A Categorical Theory of Patches

## What this paper does
Gives a formal model of version control (git/Darcs): files are objects and patches (insertions/deletions of lines, as partial injective increasing maps) are morphisms of a category L. Merging two concurrent patches that start from the same file ("coinitial") is defined as a pushout: the smallest file containing both modifications, with "residual" patches g/f and f/g that carry each change over the other. Because conflicting patches (both editing the same place) have no pushout in L, the paper builds the free finite cocompletion P, whose objects are files with only partially ordered lines, so every merge exists and conflicts are represented explicitly rather than failed.

## Goal-by-goal answers
### Goal: How is merging two concurrent changes from a common ancestor defined, and when is it order-independent?
Two users apply patches f1: A -> A1 and f2: A -> A2 to the same file A; after each imports the other's change the result must be the same file E regardless of who imports first, so there must be residual patches h/g and g/h with "the same effect" as h (resp. g) once g (resp. h) has been applied, and the commuting square must be a pushout [full text, Section 1; Section 3, diagram (2)]. Example: a b -> a c c b and a b -> a b c d merge to a c c b c d, "the smallest file containing both modifications on the original file" [Section 3]. Merging is well defined and order-free exactly when the two patches touch disjoint places; the generating insertions/deletions obey commutation relations such as s_i s_j = s_{j+1} s_i for i <= j [Section 2, Proposition 4, Eq 1]. The paper notes Darcs formalises patches through these commutation properties and operational transformation axiomatises the same residuals [Section 1, Related work].
### Goal: What is a conflict and how is it handled?
A conflict is two coinitial patches that modify the same line (a b -> a c b vs a b -> a d b): no pushout exists in L [Section 3, diagram (3)]. Instead of failing, the cocompletion P adds "files whose lines are not linearly ordered, but only partially ordered", which represent the conflicting state (like git's <<<<<<< c ======= d >>>>>>> markers) and leave the choice to a later resolution step [Section 3, Eq 4; Definition 5]. Thus P is finitely cocomplete and "the merging of any modifications of the file is well-defined" [Section 7]. Future work lists cherry-picking, branches and patch inverses [Section 7].
