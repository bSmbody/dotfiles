# Scalable SAT Solving in the Cloud

## What this paper does
Mallob: a decentralized, malleable job scheduler plus a massively parallel portfolio SAT engine (re-engineered from Hordesat). Hundreds to thousands of diversified solver threads (Lingeling configurations, seeds, phases, some YalSAT) each keep private search state and periodically exchange learned clauses. Clause exchange is aggregated up a job tree with duplicate filtering and a buffer-size discount per level. On 32 nodes (640 cores) it beats an improved Hordesat on 128 nodes (2560 cores) with the same backend solvers.

## Goal-by-goal answers
### Goal: How is clause exchange organized at scale, and what evidence shows that sharing matters?
Every s (e.g. 1 s) leaves send exported clauses to parents; inner nodes merge buffers sorted by clause length, filter duplicates by commutative hashing, and cap the buffer at b(u) = ceil(u * alpha^log2(u) * beta), then the result is broadcast [full text, Section 4.1]. With alpha = 0.5 "only a very small clause buffer ... is shared in each round which proves to be highly detrimental to Mallob's performance and underlines the importance of clause sharing"; best alpha = 7/8 [Section 5.2, Figure 4].

### Goal: What does the paper report about how importing shared knowledge interacts with each solver's private state?
Hordesat's Minisat interface was "disruptive to the solving procedure: Whenever a certain threshold of collected clauses is reached, the solver is interrupted to add all clauses and then restarted", which "might have caused the bad performance of Hordesat with Minisat" [Section 4.2 "Diversification"]. Mallob uses Lingeling, which imports clauses without restarting, and a lock-free ring buffer per solver from which clauses are imported one by one; unconsumed clauses are eventually discarded [Section 4.3 "Lock-free Clause Import"]. Diversity is kept by giving solvers different configurations, seeds and default phases [Section 4.2].
