# Scalable Proof Producing Multi-Threaded SAT Solving with Gimsatul through Sharing instead of Copying Clauses

## What this paper does
Gimsatul is a multi-threaded portfolio CDCL SAT solver in which solver threads ("rings") physically share learned clauses through pointers (one copy in memory, reference counts updated atomically) instead of copying them into each thread's database, as portfolio solvers such as ManySAT/Plingeling do. Each ring keeps its own private search state (trail of assignments, watch lists for large clauses, heuristics, restarts). Shared clauses are exported eagerly when learned with low glue, and imported one at a time before decisions. It scales linearly with threads and yields proofs about as small as single-thread ones.

## Goal-by-goal answers
### Goal: What is shared between threads and what stays private, and why does that division work?
Shared: the original clauses and imported learned clauses (by reference, "physically share clause data (through pointers) during clause exchanges instead of copying them"), global watch lists for irredundant binary clauses, and the trail of root-level unit literals [full text, Sections 0.1, 0.4.1, 0.4.3]. Private: each ring's partial assignment, its watched-literal lists for large clauses, its clause-database reduction and memory allocation ("each ring ... completely independently allocates and reduces clauses") [Section 0.4.1]. A clause, once derived, is an immutable logical fact valid for every thread, whereas the assignment trail is mutable search state that differs per thread. Importing a clause means the receiving ring fits it into its own private machinery: "The current partial assignment on the trail has to be fixed if the clause is propagating/conflicting. Otherwise, some literals ... have to be selected as watched literals", and importing amounts to "increasing the overall number of occurrences of that clause" [Section 0.4.3].

### Goal: What does physical sharing buy over copying, and what exchange policy is used?
Copying "increases the amount of memory needed by each solver thread" and duplicates clauses in proofs; physical sharing addresses both [Section 0.1]. The policy is deliberately simple: export low-glue clauses immediately into n-1 per-receiver pools (4 slots by glue tier), import at most one clause before each decision from a randomly chosen ring's pool, lowest glue first, with lock-free atomic exchange; slots are overwritten, so the queue is implicitly bounded [Section 0.4.3]. The conclusion reports linear scaling with the number of threads despite only simple diversification [Section 0.8].
