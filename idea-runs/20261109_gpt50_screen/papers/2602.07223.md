# Vegas: Self-Speculative Decoding with Verification-Guided Sparse Attention

## What this paper does
Vegas (ICML'26) is a lossless self-speculative decoding method with a sparse draft. The draft is the same model with sparse attention over a KV subset. The subset is chosen from attention logits that the full-attention verification pass has already computed (a "free oracle"). Logits are aggregated across draft tokens to avoid overfitting to the last token. A "Collect-2-Query" mechanism keeps only the logits of the first draft token and the bonus token, which keeps the collection overhead low. A three-step tuning procedure sets the sparsity ratio (7%) and gamma. Vegas is implemented in vLLM with continuous batching. Code: https://github.com/platformxlab/vegas [abstract line].

## Goal-by-goal answers
### Goal: Which models, generation lengths and batch sizes are evaluated, and what speedup is measured?
Models: Qwen3-4B, Qwen3-8B, Qwen3-30B-A3B-Thinking-2507-FP8 and gpt-oss-20b, on H100 NVL [Section 5.1]. Short-input / long-output setting: AIME25 and CodeElo, average output ~19,680 tokens, max batch 128 on one H100, continuous batching [Section 5.2]. There Vegas gets 1.25x-2.70x decoding throughput over vLLM and 1.15x-1.23x over MagicDec-Stream, the strongest baseline. Long-input setting: LongBench-v2 with 96K-120K inputs, PD-disaggregated, decode batch 4-20. There it gets 18-29% over the best baselines [Section 5.3]. The overall range is 1.25x-2.81x over vLLM [Section 1].

### Goal: Where does the gain shrink (architecture, batch, overhead)?
gpt-oss-20b gains less because only half its blocks are dense attention. Sparse drafting cuts per-step draft latency only to 48% of vanilla [Section 5.2]. KV selection overhead: Vegas 5.9-9.4%, MagicDec-Quest 21.7%, SpecExtend 11.2% (Qwen3-8B) and 29.1% (gpt-oss) [Section 5.2, Fig 10b]. Once the sparsity ratio is below ~3-10%, gamma matters more than the ratio itself [App E.2].

### Goal: What limitations do the authors state?
[App F]: sparse self-spec reduces only KV access, so it helps only when context is long enough. It targets throughput-oriented serving. At small batch it "may not provide enough benefits", and every sparse self-spec method shares this problem. For Qwen3-8B it starts to help at batch 8 on AIME25 and at batch 1 on LongBench-v2. Implication: on hybrid / partly sparse models (gpt-oss) the room for this kind of method shrinks.
