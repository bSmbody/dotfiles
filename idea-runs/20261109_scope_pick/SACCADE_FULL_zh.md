# SaccadeKV：扫视式视觉记忆（完整版：idea + 实验设计）

> 2026-11-09。面向思考型多模态模型（Thinking VLM）在高清图、多图和长视频推理时的效率问题。
> 配套文件：`METHOD_saccade_zh.md`（方法细节）、`IMPL_saccade_zh.md`（实现方案与伪代码）。

---

# 一、要解决的问题

## 1. 背景："看图推理"的模型越来越贵

现在的多模态推理模型（Qwen3-VL-Thinking、DeepEyes 等）答题分两步：
1. **读图**：把图像切成很多小块，每块变成一个"视觉 token"。一张高清图大约 3,500 个，一段视频有几万个。
2. **思考**：写一长段思维链。写到一半发现没看清，就"放大看一眼"：把某块区域裁下来，重新编码成新的视觉 token，**追加到上下文末尾**，然后接着想。

## 2. 问题出在"只能追加"

每个 token 都要在显存里存一份 KV（Qwen3-VL-8B 每个 token 约 144 KB），之后每生成一个字都要把它读一遍。
- **每看一次，上下文就长一截**：一次放大新增几百到几千个 token，旧的模糊视图还一直留着。看 10 次，视觉 KV 就涨 10 截。
- **显存撑满，并发上不去**：视觉 KV 吃掉显存，同时能服务的请求变少，每道题的成本变高。
- **最需要看清楚的场景最贵**：8K 高清图、多图对比、长视频，恰恰都需要反复看。

现在所有方法都是这么做的：
- DeepEyes、ViCrop、ZoomEye：追加裁剪图；
- FoveateR（ECCV 2026）：先看低清图，放大时也是追加。它在局限性里自己写了："缓存会增长，怎么保留、更新、丢弃留作未来工作。"

## 3. 出发点

**视觉 KV 不该是一本只能往后写的日志，而应该是一块可以修改的记忆。**

人眼就是这么工作的：只有中央凹那一小块看得清，周边是模糊的。想看哪里，眼睛扫过去，那里就变清楚，原来看的地方又变模糊。大脑里始终是"一张图"，不会因为看了十次就存了十张图。

# 二、方法：SaccadeKV（扫视式视觉记忆）

## 1. 视觉记忆分两层

| | 内容 | 大小 | 是否变化 |
|---|---|---|---|
| **底图** | 整张图的低清版 | 约为原图 token 的 1/4（例如 3,500 → 870） | 一直保留，从不删除 |
| **中央凹缓冲区** | 最近注视过的几块高清区域 | 固定容量 F（例如 512 个 token） | 随注视点变化 |

视觉记忆的总大小 = 底图 + F，**是一个常数**，和模型看了多少次无关。

## 2. 一次"扫视"发生了什么

模型在推理中说"放大看这里"，并给出一个框：
1. **编码**：把这块区域裁下来，用高分辨率重新编码，得到高清 token。
2. **原地放入**：高清 token 不追加到末尾，而是放到这块区域在图上原本的位置，同时把底图里这块的低清 token 遮掉。
3. **退回**：缓冲区满了，就把最早看的那块退回去：删掉它的高清 token，放出它原来的低清 token。底图从来没删过，所以退回是精确的。
4. **继续思考**：上下文里没有多出任何视觉 token，只多了一句"已放大某区域"。

从模型的角度看，它面前始终是**一张图**，只是看过的地方变清楚了。

## 3. 三个关键设计

### ① 位置怎么放：连续坐标
Qwen-VL 给每个视觉 token 一个二维坐标（第几行、第几列），位置编码按坐标计算，坐标可以是小数。我们统一用原图网格做坐标系：
- 低清 token 覆盖 2×2 个原生格子，坐标取中心，例如 (10.5, 20.5)；
- 高清 token 取原生格子的整数坐标，或者更细的子网格坐标。

同一块像素，不管清晰度如何，都落在同一片坐标上。后面的文字读它们时，相对位置和读普通图像完全一样，不会错乱。PRCR 就栽在这里：它把旧视觉 KV 挪到新位置，导致解码崩溃。

### ② 新 token 怎么算：重算"图像 + 问题"这一段
在 VLM 里，图像 token 只看得到它前面的内容，看不到后面的问题。扫视之后图像变了，所以把"混合分辨率图像 + 问题"这一段重新算一遍：
- 这一段只有 1–2K 个 token（底图 870、缓冲区几百、问题一百左右），在 H200 上几十毫秒；
- 已经写好的思维链 KV 不动。因为坐标系固定，它们的位置一个都不用改。

由此得到一个**精确的不变量**：任何时刻，缓存里"系统提示 + 图像 + 问题"这一段，都和"从一开始就用这张混合分辨率图"的结果完全一样。

（另有一个**快速模式**：只算新 token、不重算其余部分。它只用来做消融实验。）

### ③ 谁决定看哪里：模型自己
沿用 DeepEyes、Qwen3-VL 已有的"放大"动作，我们只改"看了之后记忆怎么变"。SaccadeKV 和"怎么决定看哪里"互不干扰，可以接到任何会放大的模型上。

## 4. 推广到视频：时间上的扫视
- **底图**：整段视频用低帧率、低分辨率编码。
- **缓冲区**：模型想细看哪一段，就把那段用高帧率、高分辨率编码，原地放进那段的时间坐标。
- 一小时的视频，视觉 KV 也只是"底图 + 缓冲区"。

## 5. 实现上的两个关键观察
1. **"原地"只是逻辑上的。**注意力对所有 key 做 softmax，和它们在缓存里的物理顺序无关，只看位置编码和是否可见。所以实现时：
   - 新的高清 token 直接拼到 KV 张量末尾，坐标设成区域的坐标；
   - "遮掉底图"就是把那几个 token 从缓存里删掉；
   - "退回"就是从备份里拼回来。

   解码时用标准因果注意力即可，不需要自定义 mask 或 kernel。
2. **坐标系固定在原生网格上。**扫视前后图像的坐标范围不变，问题和思维链的位置不用改，KV 原样保留。

## 6. 一句话总结
> 把"再看一眼"从"追加一段新上下文"变成"编辑一块固定大小的视觉记忆"。视觉记忆的大小和看的次数无关，而且任何时刻都等价于一张合法的混合分辨率图像。

# 三、实验设计

## 0. 统一设置

### 模型
| 模型 | 用途 | 原因 |
|---|---|---|
| DeepEyes-7B（基于 Qwen2.5-VL-7B） | E0–E4、E6 的主力 | 原生带"放大"工具调用，结构简单 |
| Qwen3-VL-8B-Thinking | E0、E1、E3、E4 | 当前主流的思考型 VLM，长思维链 |
| Qwen2.5-VL-7B-Instruct / Qwen3-VL-8B-Instruct | E1 | 不带工具的基座，检验"读懂混合分辨率"是否依赖工具训练 |
| Qwen3-VL-8B（视频） | E5 | 视频版 |

### 数据集
| 类型 | 数据集 | 用在 |
|---|---|---|
| 高清图（找小目标） | V*（191 题）、HR-Bench 4K / 8K（各约 800 题） | E0–E4、E6 |
| 真实场景高清图 | MME-RealWorld-Lite（约 1.9K 题） | E3、E4 |
| 多图对比 | BLINK 多图子集、MMIU 子集 | E4 |
| 长视频 | Video-MME 长视频子集（约 900 题）、LVBench（约 1.5K 题） | E5 |

### "原分辨率"的定义
8K 图按真正的原生分辨率编码会超过 8 万个 token，不现实，所以统一规定：
- **原分辨率** = 模型默认的视觉 token 上限（例如 16,384 个视觉 token）；
- **底图** = 原分辨率 token 数的 1/4（长和宽各缩一半）。

### 指标
| 指标 | 定义 |
|---|---|
| 准确率 | 各数据集官方评测脚本 |
| 视觉 KV 峰值 | 推理过程中视觉 token 数的最大值，按每 token 144 KB（Qwen3-VL-8B）或对应模型的数值换算成 GB |
| KV 占用积分 | 对每一步解码，把当时缓存的 token 总数加起来（token·步）。显存打满时，吞吐和它成反比，是 HF 原型阶段的成本代理 |
| **每答对一题的成本**（主指标） | 原型阶段 = KV 占用积分 / 答对题数；系统阶段 = 实测 GPU·秒 / 答对题数（固定 1 张 H200，显存打满） |
| 放大次数、输出长度 | 每题统计 |
| 卡住率 | 写满长度上限，或出现长段重复的比例 |

### 统计
- E1 用贪心解码（确定性）。
- E3–E5 按模型推荐的温度采样，每题 2–4 次。报均值和 95% 置信区间，组间差异用配对 bootstrap 检验。

## E0 摸底：现在的模型是怎么"看"的

**目的**：搞清楚在不同任务上，视觉 KV 占多大比例、模型放大几次、多看几次有没有用，从而确定主战场。

**做法**：
1. DeepEyes-7B 和 Qwen3-VL-8B-Thinking（配合 zoom 工具提示）在 V*、HR-Bench 4K/8K、MME-RealWorld-Lite 上正常答题，用原本的追加方式。
2. 每题记录：
   - 初始视觉 token 数、思维链长度；
   - 放大次数、每次放大框占全图的比例、每次追加的 token 数；
   - 结束时视觉 KV 占总 KV 的比例。
3. **放大次数上限扫描**：把 DeepEyes 的最大工具调用轮数设为 0 / 1 / 2 / 4 / 8 / 16，看准确率和 KV 峰值怎么变。

**输出**：
- 一张"任务 × 视觉 KV 占比 × 放大次数"的统计表；
- 一条"放大次数上限 → 准确率 / KV 峰值"曲线。

**用途**：
- 放大次数多、准确率随次数上升的任务，就是 E3、E4 的主战场；
- 追加 token 占比，给出追加式方法在每类任务上的真实成本基线。

**规模**：约 2.6K 题 × 2 个模型 × 6 档上限。DeepEyes 输出短，Qwen3-VL-Thinking 输出长。HF 原型下 8 卡并行，粗估 1–2 天。

---

## E1 可行性：模型能不能读懂"混合分辨率"的图

**目的**：验证方法的地基，即模型能否直接理解"一张图里有的地方清楚、有的地方模糊"。这一步不涉及推理中途的扫视，一次 prefill 就出答案。

**做法**：在 V* 和 HR-Bench 4K/8K 上，用标注的目标框（V*）或 E0 中模型自己给出的放大框（HR-Bench）作为注视区域。在**相同视觉 token 总数**下比较：

| 组 | 输入 | 作用 |
|---|---|---|
| G1 | 原分辨率整图 | 上限参照 |
| G2 | 整图缩小到与 G4 相同的 token 数 | 最简单的省法 |
| G3 | 底图 + 把框内区域作为第二张图追加在后面（token 数与 G4 相同） | 现有追加做法的静态版 |
| **G4** | **底图 + 框内区域原地换成原生分辨率**（连续坐标） | 本方法的静态版 |
| G4' | G4，但框内区域用 2 倍分辨率 | 检验更细层级 |
| G5 | G4 的高清 token 改用"图像末尾之后"的位置坐标 | 检验连续坐标有没有用 |

**设置**：4 个模型（两个基座、DeepEyes、Qwen3-VL-Thinking），短答案提示，贪心解码。

**看什么**：
- G4 和 G1 的差距：读懂混合分辨率的程度；
- G4 和 G2、G3 的比较：同样的 token 数，原地放比缩图和追加好多少；
- G4 和 G5 的比较：连续坐标的作用。

**进入下一步的条件**：
- G4 不低于 G2、G3 中较好的一组 → 直接进 E3；
- 否则先做 E2。

**规模**：约 1.8K 题 × 6 组 × 4 个模型，都是短答案，粗估几个小时。代码约 200 行，2–3 天写完。

## E2 适配：如果读不懂，就教它（按需）

**目的**：让模型适应混合分辨率输入。

**做法**：
1. **数据**：从带高清图的训练集（TextVQA、DocVQA、ChartQA、InfographicVQA 的训练集，加上 SA-1B 子集）取图像和问题。注视框随机选 1–4 个；对文字类数据，优先选包含答案文字的区域。
2. **构造**：每个样本生成一份混合分辨率输入，即底图加注视框内的高清区域。
3. **老师**：同一个模型在原分辨率整图上的输出分布。
4. **学生**：同一个模型加 LoRA（rank 32，只加在 LLM 注意力层的 q/k/v/o 上，ViT 冻结），输入混合分辨率，对答案 token 和思维链前 256 个 token 做 KL 蒸馏。
5. **规模**：约 5 万条样本，1 个 epoch，8×H200 上 1–2 天。

**验证**：用 LoRA 后的模型重做 E1，要求 G4 追平 G2 和 G3。之后所有实验用这个模型。

## E3 主实验：模型自己决定看哪里

**目的**：在真实使用中，证明 SaccadeKV 用常数大小的视觉记忆，达到和追加式相当或更好的准确率，并且成本更低。

**做法**：
- **模型**：DeepEyes-7B、Qwen3-VL-8B-Thinking（如有 E2，用 LoRA 版）。
- **数据**：V*、HR-Bench 4K/8K、MME-RealWorld-Lite。
- **配置**：

| 配置 | 说明 |
|---|---|
| 原分辨率 + 追加 | 模型原本的做法 |
| 底图 + 追加 | FoveateR 式：先看低清，放大时追加 |
| **底图 + 有界追加** | 追加裁剪图，但只保留最近几张，旧的从缓存里删掉，视觉 token 总数与 SaccadeKV 相同。**这是最关键的对照**：它同样是常数显存，SaccadeKV 必须在准确率上赢它 |
| SaccadeKV，F = 256 / 512 / 1024 / 2048 | 精确模式 |

- **流程**：模型正常推理。每次发出放大调用，追加配置追加裁剪图；SaccadeKV 执行一次扫视（裁剪 → 编码 → 原地放入 → 必要时退回 → 重算图像和问题 → 继续），然后在上下文里追加一句"已放大区域 [x1,y1,x2,y2]"。
- **采样**：每题 2–4 次。

**输出**：
- **主表**：每个配置的准确率、视觉 KV 峰值、KV 占用积分、每答对一题的成本、放大次数、输出长度、卡住率；
- **主图**：横轴视觉 KV 峰值，纵轴准确率。SaccadeKV 的 4 个 F 连成一条曲线，追加式是两个点。

**规模**：约 2.8K 题 × 6 个配置 × 2 个模型 × 2 次采样，约 6.7 万次生成。Qwen3-VL-Thinking 输出较长，HF 原型 8 卡并行，粗估 3–5 天。可以先在 V* 和 HR-Bench 4K 上跑通，再扩到全部数据。

## E4 核心卖点：看很多次、显存打满

**目的**：展示 SaccadeKV 最大的优势。追加式的显存随放大次数线性上涨，SaccadeKV 始终是常数，所以在需要反复看的场景里，成本差距会越拉越大。

**做法**：
1. **系统实现**：在 vLLM 上实现 SaccadeKV（实现方案 §7）。第一版只用"底图 + 原生"两级，坐标全是整数，不用改 kernel。
2. **任务**：天然需要多次注视的任务：
   - HR-Bench 8K 的跨实例题（涉及多个物体）；
   - MME-RealWorld 中的多目标题；
   - BLINK 和 MMIU 的多图对比。
3. **放大次数**：上限设为 2 / 4 / 8 / 16。同时在提示里要求模型逐个核实候选目标，把它推到多次注视的状态。
4. **显存打满**：单张 H200，一次性提交全部请求，让调度器自动开到最大并发。
5. **配置**：
   - 原分辨率 + 追加；
   - 底图 + 追加；
   - 底图 + 有界追加（只保留最近几张裁剪图，token 总数与 SaccadeKV 相同）；
   - SaccadeKV（F 取 E3 中最好的一档）；
   - SaccadeKV + 底图用 2 bit 存（叠加压缩）。

**测量**：
- 最大并发数；
- 吞吐（tokens/s，以及每小时答对的题数）；
- 每答对一题的 GPU·秒；
- 延迟的 p50 和 p90。

**输出**：一张"放大次数上限 → 每答对一题的成本"曲线图，追加式一路上升，SaccadeKV 基本持平。再加一张并发数对比表。

**规模**：vLLM 实现 3–4 周；跑实验 2–3 天。

## E5 视频版：时间上的扫视

**目的**：证明同一个机制在时间维度上同样成立。长视频是视觉 KV 最大的场景。

**做法**：
- **模型**：Qwen3-VL-8B。
- **数据**：Video-MME 长视频子集、LVBench。
- **底图**：整段视频均匀抽 256 帧，每帧压到约 64 个 token，共约 16K 个 token。
- **时间扫视**：给模型一个"细看某段时间"的工具 `zoom_time(start, end)`。被选中的片段按 2 fps、每帧约 256 个 token 重新编码，原地放进那段的时间坐标，同时遮掉底图对应的帧。缓冲区容量 F 取 4K / 8K。
- **不训练的变体**：模型不会调用工具时，用解码时对底图各帧的注意力质量，自动选择要细看的片段。

**配置**：

| 配置 | 说明 |
|---|---|
| 均匀高帧率 | 在模型 token 上限内尽量多抽帧 |
| 底图 + 追加片段 | 现有"先粗看再放大"智能体的做法 |
| 底图 + 有界追加片段 | 只保留最近几个片段，token 总数与 SaccadeKV 相同 |
| SaccadeKV 时间扫视 | 本方法 |

**输出**：准确率、视觉 KV 峰值、每答对一题的成本；按视频长度分桶（短 / 中 / 长），看成本随视频长度怎么变。

**规模**：约 2.4K 题 × 3 个配置 × 2 档 F，粗估 3–4 天。

## E6 消融：每个设计是否必要

**统一设置**：DeepEyes-7B，V* 和 HR-Bench 4K，F = E3 中最好的一档。

| 消融 | 对照组 | 回答的问题 |
|---|---|---|
| 遮掉底图 | 不遮，高低清并存 | 原地替换比"叠加"好在哪里 |
| 连续坐标 | 高清 token 用图像末尾之后的位置 | 坐标设计有没有用 |
| 精确模式 | 快速模式（只算新 token） | 重算"图像 + 问题"值不值得 |
| 按时间先后退回 | 按注意力质量退回 | 缓冲区策略的影响 |
| 原生分辨率注视 | 2 倍分辨率注视 | 注视层级的影响 |
| 底图 1/4 | 底图 1/9、1/16 | 底图能压到多小 |

**规模**：每项一组配置，粗估共 1–2 天。
