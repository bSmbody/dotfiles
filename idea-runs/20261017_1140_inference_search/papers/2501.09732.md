# Inference-Time Scaling for Diffusion Models beyond Scaling Denoising Steps

## What this paper does
Ma et al. frame inference-time scaling of diffusion/flow models as search over sampling noises, with two design axes: verifiers (oracle FID/IS, supervised CLIP/DINO classifiers, self-supervised feature similarity; for T2I: Aesthetic, CLIPScore, ImageReward, and a rank-averaged Verifier Ensemble) and algorithms (Random Search = best-of-N, Zero-Order Search in a noise neighbourhood, Search over Paths that re-noises/denoises intermediate states). Experiments on SiT (ImageNet), FLUX.1-dev and PixArt-Sigma (DrawBench, T2I-CompBench) show gains with compute, and name "verifier hacking".

## Goal-by-goal answers
### Goal: What verifier-hacking evidence does it report under search?
On ImageNet, random search against DINO/CLIP logits raises IS and precision while FID suddenly worsens and recall falls past some number of search iterations; the verifiers are point-wise and ignore population diversity [full text, Section 3.1; Appendix B, Fig 13]. On DrawBench, searching with Aesthetic degrades CLIPScore and vice versa (~-2%) [full text, Section 4.1, Fig 8; Appendix B]. On T2I-CompBench, Aesthetic search gives minimal improvement or degradation [full text, Section 4.1, Table 1].

### Goal: What mechanisms does it use against verifier hacking, and how are multiple verifiers aggregated?
(a) Locality: Zero-Order Search restricts candidates to a neighbourhood of a pivot noise and Search over Paths searches at intermediate steps, which "alleviate this issue to some extent"; enlarging the neighbourhood brings the diversity problem back [full text, Section 3.2; Appendix B]. (b) Verifier Ensemble: rank each verifier's scores across candidates and select by the unweighted average rank of Aesthetic, CLIPScore and ImageReward [full text, Section 4 setup; Appendix A.4]. The weights are fixed and identical for all prompts/candidates.

### Goal: What limitation does it report for these mechanisms?
The fixed ensemble inherits a component's bias: on T2I-CompBench "ImageReward outperforms Verifier Ensemble across all evaluation categories", attributed to the ensemble including Aesthetic, which hurts on that task [full text, Section 4.1, after Table 1]. The authors conclude no configuration is universal and call for "more carefully designed verifiers" for each task [full text, Section 7], and suggest population-level verifiers as "a more fundamental solution" for the diversity side of hacking, left to future work [full text, Appendix B].


### Goal: Does the Verifier Ensemble help on the general-purpose benchmark, i.e. where does it work and where does it fail?
On DrawBench with FLUX.1-dev, "ImageReward and Verifier Ensemble ... consistently improve scores across all evaluation metrics", while Aesthetic and CLIP verifiers are "less desirable ... due to the effect of verifier hacking" [full text, Section 4.1, DrawBench paragraph, Fig 8]. On T2I-CompBench the ensemble falls below ImageReward alone in every category because it contains Aesthetic [full text, Section 4.1, after Table 1]. So the same static rank-average helps or hurts depending on whether one member's bias is misaligned with the task.
