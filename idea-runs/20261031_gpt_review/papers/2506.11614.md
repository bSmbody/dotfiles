# Accelerating Delta Debugging through Probabilistic Monotonicity Assessment (PMA)

## What this paper does
Delta debugging (ddmin-style reduction) assumes the search space is monotone: if a subset keeps the failure, every superset does, so tests implied by an earlier failed superset can be skipped. PMA drops that assumption as a hard rule. It counts, during one reduction run, how often new passing tests agree or disagree with monotonicity (a net counter M), turns M into a confidence C(M) = 1/(1+e^-M), and skips a test that monotonicity would deem redundant only with probability C(M); otherwise the test is executed. Integrated into CHISEL, it cuts processing time by 59.2% and gives 6.7% smaller reduced programs; against ProbDD, 22.0% faster and 3.0% smaller.

## Goal-by-goal answers
### Goal: What assumptions does ddmin rest on, and what does it guarantee when they fail?
ddmin rests on monotonicity (a superset of a property-keeping test also keeps it), unambiguity (the intersection of two property-keeping tests keeps it) and consistency (every test returns true or false) [full text, Section 2.1, Assumptions 1-3]. When monotonicity and unambiguity fail, finding the smallest property-keeping subset is NP-complete, so the target becomes a local optimum, 1-minimality: removing any single element makes the test fail [Section 2.1, after Eq 1]. ddmin ends only when the granularity reaches single elements and all of those tests fail [Section 2.2, Step 3], so 1-minimality is established by executed tests, not inferred from monotonicity; monotonicity mainly buys efficiency (skipping tests implied by earlier results) [Sections 1, 2.3].

### Goal: How does PMA decide when it may use monotonicity, and what does it cost when the assumption is violated?
After each passing test T, PMA checks whether some earlier-executed superset of T failed (a violation) or not (a compliance) and moves M by -1 or +1 [Section 3.1.1, Eqs 3-4]. Before a test whose result monotonicity would predict as failing (some executed superset failed), it skips the test only if C(M) exceeds a uniform draw [Section 3.1.2, Eqs 6-7]. So inference from monotonicity is used in proportion to the evidence that it holds in this search space, and the actual test is run otherwise. Failure mode: on clang-27137, PMA wrongly skipped four property-keeping tests; three were real monotonicity violations (removing if-statements enabled an optimization that exposed the bug), costing 174 tokens (1.3% larger output) [Section 4.3, Figure 5a]. The paper also notes that "unknown" (inconsistent) test outcomes masquerade as monotonicity violations [Section 4.3].
