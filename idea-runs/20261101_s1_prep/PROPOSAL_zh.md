# 长推理中低比特 KV 的按需精度救援：研究提案

2026-11-05

## 一句话与背景

**所有请求默认用 2 bit 存 KV，把显存腾出来多装请求；在线识别正在失控的少数请求，用它已生成的 token 把 KV 重算成 FP8，再从当前位置接着写。目标是成本接近 2 bit，准确率接近 FP8。**

暂定英文标题：*Spend Precision Only Where It Pays: Mid-Trajectory KV Precision Rescue for Long-Reasoning Serving*。

状态：纸面方案，尚未做任何实验。第一阶段诊断实验（P0）用来决定方案是否成立。文中标"粗算"的数字都来自已发表论文，不是我们的实测。

**为什么是 KV**：推理模型做一道 AIME 题常要写几万 token。以 Qwen3-8B 为例，每个 token 的 KV 约 147 KB，一条 32K 的推理约 4.7 GB，64 个并发请求约 300 GB，远大于 16 GB 的模型权重。显存容量决定能装多少请求，显存带宽决定每一步解码多快，所以 KV 是长推理服务的主要瓶颈。

**2 bit 的收益与问题**：FP8 是工业标配，体积是 BF16 的一半。2 bit（有效约 2.5 bit）能再装下约 3 倍的请求，但在部分模型上会让一部分请求失控：反复检查、兜圈子，一直写到生成上限也给不出答案。

## 动机：三个观察

弱的 2 bit 方法按每答对一题算，可能比 FP8 还贵；2 bit 的显存优势大部分被少数失控请求吃掉了。

### 观察 1：2 bit 的损失主要表现为失控

WUSH-KV（2609.38121）表 2，Qwen3-8B 做 AIME25：BF16 有 11% 的样本写满上限，OSCAR 的 INT2 是 42%，TurboQuant 式 INT2 是 91–100%。LiveCodeBench v6 上更严重：BF16 11%，OSCAR 71%。写满上限是按请求发生的事件，不是均匀掉分。

### 观察 2：显存打满时，一个请求的成本与长度的平方成正比

一个请求的 KV 随长度线性增长，又要占着显存跑完全程，所以它消耗的显存×时间约为：

```latex
M \approx b \cdot L^2 / 2
```

其中 b 是每 token 的字节数（由有效比特决定），L 是生成长度。显存打满时，每步解码都要读完显存里的所有 KV，单步时间近似不变，吞吐就与 M 成反比。一个写满 64K 的失控请求，成本约是 20K 正常请求的 10 倍。

粗算：用 WUSH-KV 的数据，以平均长度的平方近似 E\[L²\]（会低估方差的影响）。

| 方案 | 有效 bit | 平均长度 | 准确率 | b × L² / 准确率（相对值） |
| --- | --- | --- | --- | --- |
| FP8（假设准确率 ≈ BF16） | 8 | 45.4k | 67.8 | 24,300 |
| OSCAR INT2 | 2.5 | 63.0k | 34.4 | 28,800（比 FP8 贵） |
| WUSH-KV INT2 | 2.5 | 53.4k | 46.7 | 15,300（比 FP8 便宜 37%） |
| 目标：本方法 | 大部分 2.5，少数 8 | 接近 BF16 | 接近 67.8 | 约 10,000–12,000（假设 20% 的请求在 8K 处升级） |

### 观察 3：KV 的损伤在状态层面可以撤销

KV 完全由 token 序列决定。把"题目 + 已生成的 token"用 FP8 重新 prefill 一遍，得到的就是精确的 FP8 KV，不需要任何备份。权重量化做不到这一点，2606.02011 只能整条重跑。

- 代价很小：Qwen3-8B 在 H200 上重算 16K 前缀不到 1 秒，而同一请求在 batch 中续写 16K token 要 5–13 分钟。
- 限制：重算只修复状态，已经采样出的错误 token 撤不回来，所以能不能救回取决于发现得早不早。

## 研究问题与假设

方法成立需要七个假设一环扣一环地成立，每个实验阶段检验其中一环，任何一环不成立就止损。

| 编号 | 假设 | 检验阶段 | 门槛 |
| --- | --- | --- | --- |
| H1 救援空间 | 强 2 bit（OSCAR+OptR）下，有一部分题从对变错 | S1 | FP8 与 INT2 的逐题准确率差 ≥ 5 个百分点 |
| H2 成本集中 | 失控请求占了不成比例的成本 | S1 | 成本占比 ÷ 数量占比 ≥ 1.5 |
| H3 早期可识别 | 只看前几千 token 就能预测谁会失控 | S1 | 前 4K token 的 AUC ≥ 0.65 |
| H4 精度是关键 | 中途升到 FP8 能救回，而且比用 2 bit 换种子重写救回得多 | S2 | 多救回 ≥ 10 个百分点，置信区间下界 > 0 |
| H5 中途优于重开 | 中途升级比用 FP8 从头重做更划算 | S2 | 比较恢复率和多花的 token |
| H6 整体更省 | 满载时每答对一题的成本确实更低 | 离线分析预估，P2 实测 | 低于全 FP8 和全 INT2 |
| H7 可泛化 | 换模型、任务、2 bit 方法，结论仍成立 | P3 | — |

## 方法

方法由四个部件组成：两档 KV 池、失控检测器、按负载的升级规则、重算升级。救援方式是从当前位置升到 FP8 接着写，不做回滚。

```
新请求进入 → 用 INT2 KV 生成 → 风险超过阈值？（每 256 个 token 检测一次，阈值随显存负载变化）
                    ↑                 │否                    │是
                    └── 继续 INT2 ←───┘                      ▼
                                              重算为 FP8 KV（16K 前缀不到 1 秒）
                                                             ▼
                                              FP8 从当前位置接着写
```

只有风险超过阈值的请求才被重算成 FP8，并从当前位置接着写；其余请求一直用 INT2。

### 1. 两档分页 KV 池

- 每个请求整体只用一种精度（INT2 或 FP8），不做 token 级混合，分页内核基本不用改。
- SGLang 中维护 INT2 页和 FP8 页两个池，按字节共享同一块显存。
- 权重整批计算；每层注意力按精度把 batch 分成两组，各调用一次对应内核。

### 2. 失控检测器

只用生成过程中现成的信息，在 CPU 上每 256 个 token 更新一次，不占 GPU。

| 信号 | 失控时的表现 |
| --- | --- |
| 熵的均值和趋势 | 模型越来越犹豫 |
| n-gram 重复率 | 同一段话反复出现 |
| 反思词频率（wait、let me double check） | 密集自我检查 |
| 新片段与之前内容的相似度 | 在重复同样的推理 |
| 长度增速、思考是否结束 | 写很长却迟迟不收尾 |

用逻辑回归把信号合成一个失败概率。训练用独立的题（往年 AIME、HMMT、OmniMath 难题），不碰测试题。检测器本身不是贡献点。

### 3. 按负载的升级规则

当下式成立时升级：

```latex
\Delta p(t, r) \cdot V \;\ge\; \lambda \cdot (b_8 - b_2) \cdot E[\text{剩余显存-时间}] + c_{\text{重算}}
```

- Δp(t, r)：在位置 t、风险 r 时升级，答对概率的提升，由分叉实验估计。
- λ：显存的影子价格，约等于当前每单位显存-时间产出的答对题数。显存空闲时 λ ≈ 0，多升级；打满时 λ 很大，只救最值得救的。
- 结果是一个随负载变化的阈值策略，系统自动在"全 FP8"和"全 INT2"之间调整。

### 4. 重算升级

1. 暂停该请求，释放它的 INT2 页，分配 FP8 页（显存占用变为约 3.2 倍）。
2. 把"题目 + 已生成的 token"用 FP8 重新 prefill，切成小块夹在其他请求的解码步之间。
3. 采样设置不变，从最后一个 token 接着写。

SGLang 已有"显存不足时撤回请求、之后重新 prefill"的机制，升级可以复用它。

### 5. 四个策略变体（用于归因）

| 策略 | 做法 | 回答的问题 |
| --- | --- | --- |
| P-direct | 风险超过阈值就直接升级 | 最简单的方案够不够 |
| P-H | 先跑一小段 FP8，风险下降再提交 | 先试再提交值不值 |
| P-LH | INT2 和 FP8 各跑一小段，比较后决定 | 多花的对照成本有没有回报 |
| P-LL | 不升精度，只用 INT2 换种子重采样 | 救回来是不是只靠运气 |

除非数据证明更复杂的策略更好，默认用 P-direct。

### 6. 扩展（非主线）：K/V 不对称

关于"K 更重要还是 V 更重要"，现有论文结论互相矛盾。推导认为答案取决于头的注意力集中度：V 误差的危害 ∝ Σp²（越集中越大），K 误差的危害 ∝ Var\_p(δs)（越分散越大）。若成立，可以只升 K 或只升 V，进一步降低升级代价。公式需引用 RECAP 和 HeadQ（已撤稿）作为先前工作。

## 创新点与相关工作

创新不在新量化器，而在新的问题视角加一个便宜的救援机制：把低比特 KV 的代价从"平均掉几分"重新理解为"少数请求失控、成本与长度平方成正比"，再利用 KV 可从 token 重算的性质把它们救回来。

### 五个创新点

1. **重新定义低比特 KV 的代价（最核心）**：首次在显存打满、以 FP8 为基线、以每答对一题成本为指标的条件下，说明损失和成本集中在少数失控请求上。系统查新未发现论文报告每答对一题的成本。
2. **KV 损伤可撤销，精度能往上走**：现有混合精度方法基本只降不升；要升级就得在 CPU 存原值或整条重跑。我们用重算升级，不需要备份，并量化它的效果和边界。
3. **救援功劳的三分拆解**：通过分叉实验，把收益拆成"精度的贡献""重新采样的贡献""中途接续相对重开的贡献"。现有工作没有把量化误差和采样随机性分开过。
4. **按负载的升级规则**：把"答对率"和"显存负载"放进同一个决策，阈值可以推导。
5. **工程**：SGLang 中按请求分精度的两档 KV 池，实测真实墙钟时间。

### 与最近邻工作的区别

| 工作 | 它做了什么 | 我们多做了什么 |
| --- | --- | --- |
| DiffKV 2412.03131 | 按请求、头、token 的注意力稀疏度分档 | 依据是请求是否失控，目标是答对率 |
| ThinKV 2510.01290 | 按思维类型分配精度 | 检测失控，并能中途升级 |
| QAQ 2403.04643 | 在线按 token 重分 K/V 位宽，CPU 留原值 | 不需要 CPU 副本；决策单位是请求 |
| PM-KVQ 2505.18610 | 显存紧张时逐步降精度 | 方向相反，可以升精度 |
| 2606.02011 | 权重量化下检测循环，用 FP16 整条重跑 | 针对 KV，中途升级，并比较中途与重开 |
| KV-Rescue 2608.15797 | 换一个保留完整 KV 的小模型救援 | 同一个模型，只换精度 |
| The Price of Precision 2610.15629 | 用时间成本模型分配精度 | 目标含答对率和失控；在线、按请求 |

## 实验设计

实验按 S0 → S1 → S2 → 离线分析 → P2 → P3 推进，前三步（S0、S1、S2）约一周机器时间就能判断这条路通不通。P0 只用 Qwen3-8B，Qwen 权重始终不动，只改 KV 的存储精度。

```
S0 定生成上限：BF16 每题 2 遍，选 BF16 写满 ≤ 10% 的上限
  ▼
S1 主采样（H1–H3）：3 精度 × 60 题 × 16 次，共 2,880 条
  ▼
闸门：可救 ≥ 5pp？ ──否──► 停：强 2 bit 已够好，方法线停止，可转为分析论文
  ▼ 是
S2 分叉实验（H4、H5）：4K/8K/16K 处切开，5 个分支各 4 次      ← 核心因果实验
  ▼
闸门：多救 ≥ 10pp？ ──否──► 停：救回只是运气，机制作废或改为低精度重采样
  ▼ 是
离线分析（脚本）：理想上界；策略和阈值初选
  ▼
P2 系统实测（H6）：8×H200 满载，每答对一题 GPU 秒数
  ▼
P3 泛化（H7）：加 Qwen3-4B，换模型、任务和 2 bit 方法
```

S2 是核心因果实验；任一闸门不过就按右侧的预案处理，不再往下投入。

### 固定条件

| 项目 | 设置 | 理由 |
| --- | --- | --- |
| 模型 | Qwen3-8B（thinking 模式），原版 BF16 权重 | 已有数据显示它在 2 bit 下掉分多、写满上限多，有救援空间；2 bit 已近乎无损的 Qwen3-4B-Thinking 放到 P3 |
| KV 精度 | BF16（参照）、FP8（升级目标）、INT2（OSCAR+OptR，有效 2.5 bit） | 选强 2 bit，不拿稻草人当对手 |
| 框架 | OptR 的 SGLang fork（固定 commit），另用 vLLM 原生 FP8 交叉校验 | 精度差异只来自精度本身 |
| 题目 | AIME 2024 + 2025，共 60 题 | 低比特 KV 在这里掉分最狠，答案是整数，可自动判分 |
| 采样 | temperature 0.6，top-p 0.95，每次一个固定种子 | Qwen 官方推荐值 |
| 生成上限 | 由 S0 确定 | 避免把"上限太短"误判为"失控" |
| 硬件 | 8×H200，每张卡一个独立服务 | 8B 模型单卡可放下，8 个服务并行跑不同的题和样本 |

### 一条做题记录是怎么产生的

1. 在一张 H200 上启动推理服务，加载 Qwen3-8B，启动参数指定 KV 精度。同一时间 8 张卡只跑一种精度，跑完再换下一种。
2. 题目按 Qwen 官方对话格式包装，开启思考模式，并要求"一步步推理，把最终答案写在 \\boxed{} 里"。
3. 按上表的采样设置生成，每次用一个固定随机种子；"每题 16 次"就是 16 个不同的种子。
4. 判分：取最后一个 \\boxed{} 里的内容，规范化为整数后与标准答案比较。没有 \\boxed、思考未结束、写满上限都算错，并分别记下原因。判分规则先在 20 条 BF16 输出上人工核对。
5. 每条记录保存：全部 token id、每个 token 的概率及前 20 个候选的概率、长度、是否写满上限、思考是否结束、预测答案、是否答对、代码和引擎版本号。

### 开跑前：一致性检查

- 取一条 BF16 生成的完整记录，在第 1K、4K、8K 个 token 处，把"题目 + 前面的 token id"原样交回同一个 BF16 服务，只生成 1 个 token。
- 重新输入后的下一个 token 分布应与原记录在同一位置一致（top-1 相同、KL 接近 0）。
- 这一步验证"直接输入 token id 接着写"不会改变模型看到的内容，S2 和系统里的升级都依赖它。不通过就先排查，常见原因是重新套了对话模板或改动了思考标签。

### S0：定生成上限

- **做法**：Qwen3-8B、BF16、上限 81,920，60 题每题做 2 遍，共 120 条。
- **统计**：长度的平均、中位数、90 分位、最大值；上限分别取 32K/48K/64K/80K 时会被截断的比例；实测吞吐（token/s）。
- **决定**：取 BF16 截断比例 ≤ 10% 的最小一档，作为后续所有实验的上限；用实测平均长度和吞吐重算 S1、S2 的机时。
- **为什么**：上限太短时，BF16 自己也会大量写满，就分不清"失控"和"上限不够"。

### S1：主采样（H1、H2、H3）

**运行**：3 种精度 × 60 题 × 每题 16 次，共 2,880 条；另用 vLLM 原生 FP8 每题跑 4 次（240 条）做交叉校验。一种精度跑完再换下一种。

**H1 有多少可救**

- 每道题分别算 FP8 下 16 次的正确率和 INT2 下 16 次的正确率，相减后对 60 题取平均。同一批题配对比较，题目难度的差异被抵消。
- 置信区间按题重抽样（bootstrap）。FP8 和 BF16 两种口径都报。
- 判定：低于 5 个百分点 → 停。

**H2 成本是否集中**

- 在 INT2 记录里标出"失控"：写满上限，或打转（用 2606.02011 的 n-gram 循环定义）。
- 每条记录的成本按显存-时间 ∝ 长度² 计。成本集中度 = 失控记录的成本占比 ÷ 它们的条数占比，并画"条数占比 vs 成本占比"曲线。
- 判定：低于 1.5 → "成本集中"不成立。

**H3 能否早期识别**

- 对每条 INT2 记录，只看前 2K/4K/8K 个 token，算五类信号：熵、重复率、反思词频率、自相似度、长度和思考状态。标签是"最终答错或写满上限"。
- 用逻辑回归预测。交叉验证**按题目分组**：同一题的记录不同时出现在训练和测试中，否则模型只学到"哪道题难"。
- 另报一个只用"当前长度"的基线，证明其他信号有额外价值。
- 判定：4K 时 AUC 低于 0.65 → 放弃提前准入，只在明显失控时触发。

**两个对照**

- 检测器对照：同一个检测器跑在 FP8 记录上。FP8 的失败与量化无关；如果它在 FP8 上的报警率和在 INT2 上差不多，说明它抓的是难题而不是量化失控。
- FP8 校验：fork 里的 FP8 比 vLLM 原生 FP8 低 5 个百分点以上，或平均长度多 10% 以上 → H1、H4 改用 BF16 口径。

**闸门**：H1 不成立就不跑 S2。

### S2：分叉实验（H4、H5，核心因果实验）

做法：在失败记录的同一个位置切开，造出几个"平行世界"，每个只改一个条件，把精度的作用和运气、重做分开。

**选样本**（规则在 S1 开跑前固定并提交）

- 从 INT2 失败记录（答错或写满上限）中按固定随机种子抽至多 60 条，每题至多 3 条，按题分层，防止结论被一两道难题主导。
- 另抽 50 条 INT2 下答对的记录作对照。

**切点与接续方式**

- 切点取第 4K、8K、16K 个 token，超过记录实际长度的切点跳过。
- 把"题目 + 原记录前 t 个 token"的 token id 原样交给目标精度的服务，不重新套对话模板。服务会用自己的精度重新 prefill 这段前缀，这就是"重算升级"，然后从第 t+1 个 token 往下写，上限与 S1 相同。
- 每个切点跑下表 5 个分支，每个分支换 4 个随机种子：

| 分支 | 做法 | 排除哪种解释 |
| --- | --- | --- |
| H 续写（FP8） | 前缀 token 交给 FP8 服务重新 prefill 后接着写 | 主角 |
| H 续写（BF16） | 同上，交给 BF16 服务 | FP8 实现偏弱 |
| L 续写 | 同样前缀交给 INT2 服务，换种子 | 只是运气 |
| H 重开 | FP8 从头做 | 重做就够了 |
| L 重开 | INT2 从头做 | 基础对照 |

- 重开分支与切点无关：每条源记录只跑一组，所有切点共用，计费时去重。
- 50 条答对的对照记录只跑 H 续写和 L 续写，检验升级会不会把本来做对的题搞坏。

**怎么算**

- 恢复率 = 原本失败的记录在该分支下最终答对的比例（4 次平均）。
- **精度的功劳 = H 续写恢复率 − L 续写恢复率**。挑出来的都是失败记录，其中一部分只是运气差，换个种子也能做对，必须扣掉。
- 中途接续的价值：比较 H 续写和 H 重开的恢复率，以及各自额外生成的 token 数。
- 误升级的代价：对照组升级后准确率下降多少、多花多少 token。
- 什么时候救最有效：恢复率随切点位置变化的曲线。

**预先登记的判定**

- 主分层：Qwen3-8B、8K 切点、FP8 口径。H 续写 − L 续写 ≥ 10 个百分点，且按题聚类的 95% 置信区间下界 > 0，机制才算成立；否则停。主分层样本不够时顺延到 4K 切点。
- 其余分层用 Holm 方法校正，只作探索，不能单独救活机制。
- H 续写与 H 重开差值的置信区间完全在 ±5 个百分点内 → 判为"相当"，方法简化为"检测后用 FP8 重开"。置信区间太宽时报"不确定"。
- 功效检查：跑 S2 前用 S1 的实际失败数估算主分层能否检出 10 个百分点；检不出就在 60 条上限内扩大主分层的抽样。

### 离线分析（S2 之后，不单独设闸门）

一个分析脚本，不单独设闸门，用来算真机上做不了或太贵的东西。

- **输入**：S1 的 2,880 条记录（长度、对错、逐 token 信号）和 S2 的分支结果。另需一批校准题（AIME 2022–2023、HMMT 2 月赛、OmniMath 难题）在 INT2 下的采样记录，用来训练检测器、选阈值，与测试题完全分开。
- **模拟**：一台显存容量固定、已经坐满的服务器。请求排队进入，有空位就进；每个请求按真实记录回放长度和对错；每 256 个 token 让策略决定一次是否升级；升级后的结果从 S2 中最接近的切点、对应分支的结果里抽取。成本按显存-时间计。
- **比较的策略**：四个策略变体、检测后用 FP8 重开、相同比例的随机升级、全 FP8、全 INT2、理想上界。
- **产出**：理想上界（只能离线算）；各策略的每答对一题成本估计；送到 P2 真机上的少数几组策略和阈值。
- 显存-时间这个成本代理准不准，以 P2 的真实墙钟时间为准。

### P2：系统实测（论文主结果）

- **系统**：第一版用"双服务 + 外部控制器"。一个 INT2 服务、一个 FP8 服务，显存事先按比例分好。控制器以流式方式接收每个请求的 token，每 256 个 token 算一次风险；超过阈值就取消该请求在 INT2 服务上的生成，把"题目 + 已生成 token"交给 FP8 服务接着写。不改 SGLang 内部。效果明显时再做第二版：同一服务内两档 KV 池共享显存。
- **负载**：固定题集，难易混合（MATH-500、AIME/HMMT、LiveCodeBench，比例可调）；请求持续排队，使显存始终打满。
- **测量**：完成整个题集的墙钟时间和答对题数，主指标 = 每答对一题的 GPU 秒数；同时报准确率、平均长度、写满上限比例、打转比例、升级比例、最大并发、p50/p99 延迟。每组重复 3 次。
- **对照**：全 BF16、全 FP8、全 INT2（OSCAR+OptR、NOVA-KV）、相同比例的随机升级、检测后用 FP8 重开、只换种子重采样、理想上界（来自离线分析）。
- **负载扫描**：改变并发上限或可用显存，画"每答对一题成本 vs 负载"曲线。预期：负载低时接近全 FP8 的准确率，负载高时接近全 INT2 的成本。
- **消融**：去掉某一类检测信号；固定阈值 vs 随负载变化的阈值；直接升级 vs 先试再提交 vs 两路对照。

### P3：泛化

Qwen3-4B-Thinking-2507（2 bit 已近乎无损，检验方法几乎不触发、不帮倒忙）、Qwen3-14B/32B、R1-Distill，可选一个混合架构模型（GPT-OSS-20B）；LiveCodeBench、GPQA、AIME 2026；换成 NOVA-KV 或 KVarN；64K 长度。

每个设置报告与 P2 相同的指标。Qwen3-4B 上重点看两件事：升级比例是否很低，准确率是否不降；GPT-OSS-20B 上看救援空间是否比 Qwen3-8B 更大。

## Benchmark、指标与统计

主指标是**每答对一题的 GPU 秒数**；tokens/s 会奖励长度膨胀，不作为主指标。benchmark 与 TaSQ、OSCAR、OptR、NOVA-KV、WUSH-KV 基本一致，可直接对比。

| 用途 | Benchmark | 每题采样 |
| --- | --- | --- |
| P0 诊断 | AIME 2024 + 2025（60 题） | 16 |
| 检测器训练、选阈值（与测试集分开） | AIME 2022–2023、HMMT 2 月赛、OmniMath 难题子集 | — |
| 论文主表 | AIME 2024/2025 | 16 |
| 防背题 | AIME 2026（晚于 Qwen3 发布）、HMMT（与校准集不同的一届） | 16 |
| 编程（失控最严重） | LiveCodeBench v6（按时间窗口，约一两百题） | 4–8 |
| 不帮倒忙 | GPQA-Diamond（198 题）、MATH-500 | 8 / 4 |
| 系统实测负载 | MATH-500 + AIME/HMMT + LiveCodeBench 混合 | — |

不作为主要指标：RULER、NIAH、LongBench（长输入短输出，不会失控），困惑度（看不出会不会失控）。

**每个 benchmark 都报**：准确率、平均长度、写满上限比例、打转比例、升级比例、每答对一题 GPU 秒数；系统实测另报最大并发和 p50/p99 延迟。

**统计原则**

1. 配对比较：不同精度用同一批题，按题计算差值。
2. 重复采样：AIME 每题 16 次，分叉每个分支 4 次。
3. 置信区间按题目聚类：同一道题的多条记录不独立。
4. 预先登记：主分层、顺延规则、Holm 校正、±5 个百分点等价区间、抽样规则和阈值，在看到结果前写定并提交。
5. 不显著不等于相同：置信区间太宽时报告"不确定"。
