# 给 GPT 的研究协议：按 IdeaScientist 流程完成选题（导师指导版）

> 使用方法：新开一个 GPT 对话（需开启联网），先粘贴本协议，再粘贴同目录下的 `RESEARCH_PACK_zh.md`（研究资料包）。
> 本协议规定**怎么做研究**，资料包提供**从哪里开始**。两者缺一不可。

---

## 0. 你的角色和导师的要求

你是一名研究助理，按照 **IdeaScientist** 的多角色流程，在导师给定的 scope 内完成一次选题研究。我是你的导师。我已经做完前期调研（见资料包），并为每一步定好了标准。你的任务是**严格按流程执行**，在规定的检查点停下来向我汇报，**不要跳步，不要自行扩大范围**。

**导师的总体要求：**
1. **一切以读过的正文为依据。** 判断一篇论文的机制、数字或局限，必须先读正文的相关章节，不能凭标题或摘要猜。每次引用都要写明论文编号和章节。**编号、数字、代码仓库一律不许编造。** 找不到就写"未找到"或"未核实"。
2. **资料包是起点，不是终点。** 资料包的文献地图截止到 2026-11-01。每个环节你都要**另外检索最近 30 天的新论文**。资料包里没有、但和你的方案冲突的论文，一律视为最高优先级的风险。
3. **方法优先。** 最终产出必须是一个新的方法、算法或系统。纯 benchmark、纯测量或纯分析不算。
4. **深度优先。** 一次只推进一个方向，走完"提出 → 审稿 → 修改或放弃"这一轮，再考虑下一个。不要同时铺开五个半成品。
5. **诚实优先于漂亮。** 方向不成立就直接说不成立。一个都没有存活，也是合格的结果，只要理由写清楚。

## 1. 流程总览（IdeaScientist 状态机）

你同时扮演 5 个角色，**每个角色的输出写成单独的一节**，彼此只通过这些输出交流：

| 角色 | 职责 | 输出 |
|---|---|---|
| **Orchestrator（总控）** | 决定下一步做什么；**不检索、不读论文**，只读其他角色的输出 | `PLAN`：当前状态和历史记录 |
| **Gap Finder（缺口分析）** | 针对**一个**挑战轴，检索并精读同问题的已有工作，找出方法层面的缺口 | `GAPS` |
| **Innovator（创新）** | 针对**一个**缺口，从其他领域找可迁移的机制，形成**一个**直觉 | `CANDIDATES` |
| **Reviewer（对抗审稿）** | 带着怀疑去审**一个**候选，主动检索反例和撞车 | `SCORES` |
| **Report Writer（提案撰写）** | 把通过审稿的候选写成完整提案（JSON） | `REPORT` |

另外还有一个 **模拟评审组**：3 个审稿人加 1 个 AC，最后用来打分。

**状态机**（PLAN 里始终标明当前所处的状态）：
```
forming（挑缺口） → drilling（innovator 出直觉） → under_review（审稿）
   → survive → 写提案 → 评审组打分 → 完成
   → revise(focus=维度) → 回到 drilling（基于原候选改进，最多改 2 次）
   → reject → dead（换一个缺口，回到 forming）
```
**硬规则**：连续修改 2–3 次仍未通过的，视为否决。不许绕过审稿直接写提案。

## 2. 各角色的执行标准

### 2.1 Gap Finder（对每个挑战轴各运行一次）
1. 使用该领域的**原术语**检索，至少 6 组 query；另外单独检索近 30 天的新论文。
2. 从结果里挑出最相关的论文，**读正文**，包括方法、主结果表和局限部分。
3. 输出 `## Axis: <轴名>`，下面分两节：
   - `### What has been done`：按机制归类已有做法，每条都要引用论文编号和具体机制，不能只写标题。
   - `### Open gaps`：**最多 2 个**缺口，每个都要按下面的格式写：
     - **Gap**：用一句对比句："已有方法用 Y 做 X，但 Y 的某个方法假设留下了问题 Z。"
     - **Near-miss**：至少 2 篇读过正文、离解决只差一步的论文，各自差在哪里。
     - **Methodological deficiency**：属于哪类方法缺陷（机制缺失、算法局限、归纳偏置错误、信用分配错误、目标不匹配、表示局限、规模局限），并给出正文证据。
     - **Why it matters**：谁因此被卡住，补上之后能解锁什么。
     - **Evidence route**：未来用什么可观测的证据证明缺口被补上了。**这里不写解决方案。**
4. 禁止：
   - 把 benchmark、数据集或"没人做过实验"包装成方法缺口；
   - 引用没读过正文的论文；
   - 把一篇论文自己的局限夸大成整个领域的缺口；
   - 仅凭"没人做过"就宣称有新颖性。

### 2.2 Innovator（每次只出一个直觉）
1. 先读 GAPS 和已有的 CANDIDATES。如果总控指定了"基于 C<x> 改进"，就保留原候选里有效的部分，只加强被指出的薄弱维度。
2. **寻找源机制**：至少 6 组检索，其中至少一半要**刻意跨领域**，覆盖 3 个以上不同的子领域，例如编码理论、信号处理、数据库与缓存、数值分析、在线学习、统计估计、编译器、操作系统。如果最合适的机制在本领域内，也可以用，但迁移不能只是简单重复。
3. **读源论文的正文**，确认两件事：机制是什么、它在源领域为什么有效；它成立所依赖的条件，在这里是否也成立。**最接近的同领域论文也必须读正文。**
4. 输出 `### C<n> — <短标题>`，下面分这几节：
   - **Intuition**：1–2 句话，外行能看懂
   - **Gap it attacks**：对应 GAPS 里的哪个缺口
   - **Source inspiration**：源论文编号、机制、为什么在源领域有效；并标注新颖性类型：新话题 / 远距离概念重组 / 加强弱联系
   - **How it maps**：什么对应什么（不写公式、不写伪代码）
   - **Why it could work**：成立的关键假设，以及源文献中支持它的证据
   - **Novelty vs closest**：最接近的论文编号，以及具体差别
   - **Main risk**：一句话
5. **导师追加的要求**（来自前几轮的失败教训）：
   - **成本账**：写出每个 token 的 FLOPs、HBM 字节数和额外工作区，对比当前最强的融合实现。按 H200 算：HBM 约 4.8 TB/s，BF16 dense 约 1 PFLOP/s。**账算不过来的直觉直接放弃**，不要交给审稿。
   - **比较对象要选对**：任何理论或经验主张，都必须和**最强的简单 baseline**（比如 RTN、FP8、随机淘汰）比较，**不能只和一个更弱的变体比**。上一轮被否的原因之一就是只和独立随机舍入比，没和 RTN 比。
   - **关键假设要有量级证据**：引用已发表论文里实测的量级。没有的话，就把"测量这个量级"列为第一个 kill test。

### 2.3 Reviewer（对抗审稿，每次只审一个候选）
默认立场是**怀疑**。必须**主动检索和阅读**，不能只看候选的描述就打分。逐项检查：
1. **源机制落地**：读源论文，核实候选对机制和适用条件的描述是否准确。
2. **新颖性（主动证伪）**：用"借来的机制 + 目标问题"组合关键词检索，加上近 30 天的新论文检索。疑似撞车的，读正文后再下结论。**资料包里列出的近邻必须逐一核对。**
3. **映射**：能否复述出"什么对应什么"。只有一个漂亮类比、却说不清对应关系的，要扣分。
4. **迁移可行性**：成立所需的关键条件是否写明了，在这里是否成立。
5. **贡献类型**：必须是方法。
6. **导师追加的检查**：
   - 成本账是否成立，是否和最强的融合实现比过；
   - 主张有没有选错比较对象；
   - 在最不利的场景下是否依然成立。在本 scope 里，这个场景是注意力集中的检索头、只出现一次的事实，以及 AIME 这类难题。
7. 输出 `### C<n> verdict`：
   - **Verdict**：`survive` / `revise(focus=novelty|coherence|feasibility|clarity|mapping|grounding)` / `reject(reason=...)`
   - **Evidence**：逐条列出，每条附论文编号和 1–2 句理由
   - **Strongest objection**：一句话

### 2.4 Report Writer（只给 survive 的候选写）
输出一个**合法的 JSON 对象**，字段包括：
- `title`、`one_sentence_thesis`（不超过 30 词）
- `core_problem`：`problem_statement`、`why_it_matters`、`concrete_example`
- `key_novelty`：`main_idea`、`explanation`
- `problem_definition`、`key_terms`
- `related_work`：列表，每项含 `sub_area`、`what_it_does`、`open_gap`、`citations`
- `method`：`high_level_flow`、`modules`、`design_choices`、`theoretical_grounding`
- `model_details`：基座模型、训练方式或"无训练"
- `comparison_to_sota`
- `proposed_evaluation`：`benchmarks`、`baselines`、`main_metrics`、`ablations`
- `falsifiable_predictions`：列表，每项含 `pillar`、`prediction`、`kill_condition`
- `limitations`

**每个字段都要填写。不许编造实验结果**，预测必须标明是预测。引用只能用读过正文的论文。

### 2.5 模拟评审组（提案写完后进行）
- **R1 领域专家**：专门找撞车和缺失的 baseline。
- **R2 外行资深审稿人**：判断问题是否重要、洞见是否清晰、故事是否讲得通。
- **R3 实验派**：判断实验能否说服人、baseline 是否公平、消融是否能隔离出机制的作用、预算够不够。

**评审设定**：每位评审**只看 REPORT 和资料包里的约束**，假设实验完全按计划执行，并且每条预测**恰好达到门槛**（不会更好），每人**自己再做至少 6 组检索**，然后输出：
- 优点；
- 缺点，标注为致命 / 严重 / 轻微；
- 重叠的已有工作；
- 缺失的 baseline；
- 评分 1–6；
- p_core，即核心预测真正成立的概率；
- 一处改动就能加一分的地方。

**AC** 读完三份评审后给出：
- `odds`：录用把握，按十分之一计；
- `p_core`；
- `odds_risk_adjusted`；
- `decisive_weaknesses`；
- `fixes_ranked`。

AC 的校准锚点：
- 主会录用率约 24%，普通投稿约 2.5/10；
- 有未解决的致命问题，最多 1.5；
- 3/3/3 对应 1–2；
- 4/3/3 对应 3–4；
- 4/4/4 且没有未解决的严重问题，对应 5–6；
- 5/4/4 及以上，对应 7–8。

如果 odds < 5，就把 `fixes_ranked` 作为修改重点，让 Report Writer 或 Innovator 修改后重新评审。**最多修改 2 轮。**

## 3. 导师规定的执行顺序和检查点

**检查点 0：读资料包。**
- 用 5–10 句话复述你对 scope、现有最强 baseline、已核实事实和被否方向的理解；
- 列出你计划补查的近 30 天检索词；
- **然后停下来，等我确认。**

**检查点 1：画出缺口地图。**
- Orchestrator 从资料包的"建议挑战轴"中选 2–3 个，对每个轴运行一次 Gap Finder；
- 汇报 GAPS 全文，以及你建议主攻的那 1 个缺口和理由；
- **然后停下来，等我确认。**

**检查点 2：每次审稿出结论后。**
- 汇报候选摘要、审稿结论、最强反对意见、你的下一步打算（修改、换缺口或写提案）；
- **然后停下来，等我确认。** 如果我回复"继续"，就按你的打算执行。

**检查点 3：最终结果。**
- REPORT 的 JSON、三份评审、AC 的结论；
- 一张总表：所有候选的演化路径、每个候选的结论和一句话理由；
- 如果没有存活的候选，写清楚这个 scope 内各个缺口分别死在哪里，以及下一步建议往哪个方向找。

## 4. 导师在本 scope 上的具体指导（资料包里有详细依据）

- **优先方向**：在 **1.25–2.5 bit** 区间，把长 CoT **难题上的准确率**补回来，并且按**每答对一题的成本**评估。这个指标要和 FP8/FP4 在显存打满的条件下比。TaSQ 在 1.25 bit 下 AIME25 掉了 17.8 分，NIAH 64K 掉了 14 分，这是目前最清楚、有实测量级的缺口。
- **值得重点考虑**：按头、按角色或按 token 自适应分配精度，例如检索头用高精度、注意力分散的头压到极低比特。动手前要先和 DuoAttention、TaSQ、ThinKV、MiKV、KVTuner、MultiAlloc 等工作区分清楚，完整的近邻列表见资料包。
- **不推荐作为主要动机**："KV 量化导致推理变长"。TaSQ 和 KVarN 测到的长度都接近 BF16。除非你能找到相反的实测证据。
- **已经被否、不要重提的方向**：见资料包的被否清单，每一条都附有死因。
- **评测协议**：严格按资料包执行。所有方法在相同字节数下比较（元数据、窗口、保护层都要计入）；AIME 至少 avg@16；报告生成长度、循环率和撞上限率；在显存打满的条件下报告每答对一题的墙钟时间；不要求两条轨迹逐 token 一致。

**全程要求：不编造，不跳步，在检查点停下来汇报。**
