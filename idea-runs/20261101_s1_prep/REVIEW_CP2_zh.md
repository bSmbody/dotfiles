## 二、聚焦修改的内容（只改这三处）

### 1. 补上恢复方式 (d)：按 token 重算（re-prefill）升级。它很可能让 CPU 副本不再必要

- **KV 量化误差在给定 token 序列的条件下是完全可逆的。** KV 是已生成 token 的确定性函数，所以把"提示 + 已生成前缀"的 token id 用 BF16 或 FP8 重新 prefill 一遍，得到的就是精确的高精度 KV。权重量化做不到这一点，2606.02011 只能整条重跑。低比特 KV 留下的损伤只存在于**已经采样出的 token**里，不在状态里。
- **代价量级**（Qwen3-8B，H200，前缀 N = 16K）：
  - 线性部分约 2 × 8e9 × 16K ≈ 2.6e14 FLOPs；
  - 注意力部分约 4 × 36 层 × 4096 × N² ≈ 1.6e14 FLOPs；
  - 合计约 4e14 FLOPs，按 50% 的约 1 PFLOP/s BF16 峰值计算，**不到 1 秒**。
  - 同一请求在 batch 中续写 16K token，按 20–50 ms/步计，需要 **5–13 分钟**。
- 所以升级的主要代价不是重算，而是**升级后剩余生成过程中的显存占用**（batch 变小），以及 chunked prefill 对同 batch 其他请求解码的干扰。
- 要求：
  - 在代价模型中加入 (d)，并和 (a) 只对新 token 升精度、(b) CPU 副本回取、(c) 从头重跑做定量比较；
  - 凡是保留 CPU 副本的设计，都必须说明它为什么比 (d) 更好；
  - 升级目标默认是 **FP8**。H200 是 Hopper 架构，没有原生 FP4，所以在 H200 上 FP8 是服务端的精度地板，BF16 只作为参照。
- 查新要求：确认是否已有工作把"按 token 重算 KV 以撤销量化"用作精度升级。vLLM 被抢占后的 recompute 是工程先例，不涉及精度。

### 2. 贡献归因：把 C1 拆成递进的四个策略，并给出各自的成本

| 策略 | 做法 |
|---|---|
| P-direct | 信号超过阈值 → 直接 (d) 升级，不做探针 |
| P-H | 先用 (d) 跑一段短的高精度分支 H，根据响应决定是否提交 |

C1 只有在 P-LH 稳定优于 P-H 和 P-direct，且多出的探针成本有回报时才保留。否则主方法退回 P-direct 或 P-H，L/H 双分支只作消融。**不要预设 C1 会赢。**

## 三、P0 实验（修改完成后，请把它写成可直接运行的代码和配置，由我们在 H200 上运行）

**原则**：P0 不写任何内核。所有精度切换都用"提交 prompt_token_ids 给另一个精度的引擎"实现。准确率和长度实测，墙钟时间先按代价模型推算。

**模型**：
- Qwen3-8B（thinking 模式）：WUSH-KV 显示它在 2-bit 下损失大、触顶多；
- Qwen3-4B-Thinking-2507：强 2-bit 方法在它上面几乎无损。

两者构成对照：一个预期有救援空间，一个预期没有。

**精度**：BF16（参照）、FP8（vLLM 原生）、一个**强** 2-bit codec。
- 请先核查 NOVA-KV、OptR、KVarN、WUSH-KV、OSCAR 是否有公开的 vLLM 或 SGLang 代码，选最强的一个可用的。
- 如果强方法都没有代码，就用 KIVI-2 式并保护 sink 和最近窗口，作为临时方案，并在所有结论上标明"弱 codec，救援空间可能被高估"。
- TurboQuant 式 INT2 只能作为第二个 codec，不能作为主 codec，因为它会让 91–100% 的样本触顶，相当于稻草人。

**任务与采样**：
- AIME24 + AIME25 共 60 题，每题 16 个样本；
- 采样参数用 Qwen3 官方推荐值（temperature 0.6，top-p 0.95），生成上限 32K；
- 对触顶的样本，在 64K 上限下补跑一次，检查截断效应；
- 有余力再加 LiveCodeBench v6 子集。

**记录**：逐 token 的 token id、所选 token 的 logprob、top-20 logprob。离线计算熵、n-gram 重复、反思词频率、think 是否闭合、长度增速。

**分叉实验（回答 Q4）**：对 2-bit 下答错或触顶的样本，在前缀 t ∈ {4K, 8K, 16K}（不超过实际长度）处分出 4 个臂，每臂 k = 4 次：

| 臂 | 做法 |
|---|---|
| H 续写 | 用 FP8 引擎（另跑一组 BF16）重新 prefill 前缀，然后续写 |
| L 续写 | 用同一 2-bit 引擎、换随机种子续写 |
| H 重开 | 用 FP8 从头生成 |
| L 重开 | 用 2-bit 从头生成，换种子 |

另外抽 50 条 2-bit 下答对的样本，同样做 H 续写和 L 续写，用来估计误升级的代价和"升级会不会反而有害"。

**实现细节**：
- 续写时直接传 token id，**不要重新套用 chat template**；
- 先做一次一致性检查：把 BF16 轨迹在 BF16 引擎上重新 prefill，下一 token 的分布应与原轨迹一致。

**P0 要回答的四个问题和判定规则（预先写定，不准事后调整）**：

| 问题 | 指标 | 停止或降级规则 |
|---|---|---|
| Q1 救援空间 | 按样本统计"FP8 答对、2-bit 答错"的比例 | 两个模型都低于 5 个百分点 → G1 停止 |
| Q2 成本集中 | 触顶和循环样本的 token 占比 ÷ 样本数占比 | 低于 1.5 → "成本集中"的说法不成立，G1 只剩准确率这一条贡献 |
| Q3 早期可预测 | 前 2K/4K/8K 信号预测"最终答错或触顶"的 AUC | 4K 时低于 0.65 → 撤销提前准入 |
| Q4 中途可恢复 + 归因 | 各臂恢复率；每次恢复的 token 成本 | ① H 续写比 L 续写高不到 10 个百分点 → 精度升级没有超出重采样的价值，G1 机制作废；② H 续写和 H 重开相当 → 中途升级没有超出重开的价值，降级为"检测后重开" |

**算力估计**：主实验约 2 模型 × 60 题 × 16 样本 × 3 精度 × 约 2 万 token ≈ 1.2 亿 token；分叉实验约 1 亿 token 以内。vLLM 在 H200 上跑 8B 模型属于十几到几十 GPU 小时的量级，请按实际吞吐重算并写进计划。
