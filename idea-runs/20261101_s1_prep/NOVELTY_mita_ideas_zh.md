# 由 MiTA 启发的两个想法：查新结果（2026-11-06）

检索方式：arXiv 共 24 条 query（2025-01 之后，每条 -k 30），外加 1 次网页搜索；用摘要筛选近邻。只读了摘要，没有读全文。

## 想法 1：用"重算 + 代表 query 挑选"，只把关键 token 升回高精度

**结论：没有发现直接撞车，但空间较窄。**

| 近邻 | 做了什么 | 和想法 1 的区别 |
|---|---|---|
| QAQ 2403.04643、Runtime-Certified 2605.20868 | CPU 上保留原值副本，按需把部分 token 或块提升精度 | 需要额外存副本；我们不存，靠重算 |
| KVmix 2506.08018 | 解码时动态更新"保持全精度"的 token 集合 | 只覆盖最近的关键 token，旧 token 压掉后无法恢复 |
| HyQuant 2608.27875（EMNLP 2026） | 按注意力模式选出"竖线 token"和局部窗口，保留高精度 | 在写入或 prefill 时决定，不能事后回头提升 |
| SemKV 2608.28911、SpectrumKV 2606.08635、TriRoute 2607.06601、MiKV、ZipCache | 按 token 重要性分配混合精度 | 同上，都是写入时决定 |
| KV-Direct（2603.19664） | 证明 K/V 可以从残差流**逐位精确**地重算；只存残差、按需重算 K/V | 已经公开了"KV 可重算"这一事实，我们的观察 3 必须引用它。它用重算来省显存，不是用来提升精度。另外，在 GQA 模型上残差向量比 KV 还大，它的方案省不了显存 |
| CAPTURE 2501.01792 | 存激活而不存 KV，按需重算 | 目的是卸载场景下的吞吐，与精度无关 |

**剩下的新意：**
- 在后续 query 已经显示"哪些旧 token 被反复读取"之后，**事后**把这些 token 提升回高精度；
- 不存任何原值副本，靠重算实现；
- 用在失控请求的救援上，降低升级成本。

**风险：**
1. 每次重新挑选都要重算全部前缀，频率高了代价会上来。
2. 被挑中的 token 散布在各处，按页管理时需要以页为单位提升（类似 Quest 的页），这会破坏"每个请求只用一种精度"的简单设计。
3. 部分升级能否达到全量升级的救援效果，需要实验验证。

**定位：**作为主方法的第二阶段改进（降低升级的显存代价），不单独成文。

## 附带发现：主线方法要补引的近邻

**DMR：Dynamic Mixed-Precision Routing（2602.02711）**
- 在多步智能体任务中，每一步用一个轻量路由器，在同一模型的高精度和低精度**权重**版本之间切换。
- 它发现只有约 1% 的步骤是"关键步"：在这些步骤用低精度，会把成功变成失败。
- 和我们的区别：它切换的是权重精度，KV 始终保持高精度共享，所以不省 KV 显存；决策粒度是按步，不是按请求的失控状态。
- 它的发现支持我们的 H2（损失集中在少数地方）。相关工作里必须引用并区分。
