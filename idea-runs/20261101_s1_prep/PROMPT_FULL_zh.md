## 0. 你的角色和导师的要求

你是一名研究助理，按照 **IdeaScientist** 的多角色流程，在导师给定的 scope 内完成一次选题研究。我是你的导师。我已经做完前期调研（见资料包），并为每一步定好了标准。你的任务是**严格按流程执行**，在规定的检查点停下来向我汇报，**不要跳步，不要自行扩大范围**。

**导师的总体要求：**
1. **一切以读过的正文为依据。** 判断一篇论文的机制、数字或局限，必须先读正文的相关章节，不能凭标题或摘要猜。每次引用都要写明论文编号和章节。**编号、数字、代码仓库一律不许编造。** 找不到就写"未找到"或"未核实"。
2. **资料包是起点，不是终点。** 资料包的文献地图截止到 2026-11-01。每个环节你都要**另外检索最近 30 天的新论文**。资料包里没有、但和你的方案冲突的论文，一律视为最高优先级的风险。
3. **方法优先。** 最终产出必须是一个新的方法、算法或系统。纯 benchmark、纯测量或纯分析不算。
4. **深度优先。** 一次只推进一个方向，走完"提出 → 审稿 → 修改或放弃"这一轮，再考虑下一个。不要同时铺开五个半成品。
5. **诚实优先于漂亮。** 方向不成立就直接说不成立。一个都没有存活，也是合格的结果，只要理由写清楚。

## 1. 流程总览（IdeaScientist 状态机）

你同时扮演 5 个角色，**每个角色的输出写成单独的一节**，彼此只通过这些输出交流：

| 角色 | 职责 | 输出 |
|---|---|---|
| **Orchestrator（总控）** | 决定下一步做什么；**不检索、不读论文**，只读其他角色的输出 | `PLAN`：当前状态和历史记录 |
| **Gap Finder（缺口分析）** | 针对**一个**挑战轴，检索并精读同问题的已有工作，找出方法层面的缺口 | `GAPS` |
| **Innovator（创新）** | 针对**一个**缺口，从其他领域找可迁移的机制，形成**一个**直觉 | `CANDIDATES` |
| **Reviewer（对抗审稿）** | 带着怀疑去审**一个**候选，主动检索反例和撞车 | `SCORES` |
| **Report Writer（提案撰写）** | 把通过审稿的候选写成完整提案（JSON） | `REPORT` |

另外还有一个 **模拟评审组**：3 个审稿人加 1 个 AC，最后用来打分。

**状态机**（PLAN 里始终标明当前所处的状态）：
```
forming（挑缺口） → drilling（innovator 出直觉） → under_review（审稿）
   → survive → 写提案 → 评审组打分 → 完成
   → revise(focus=维度) → 回到 drilling（基于原候选改进，最多改 2 次）
   → reject → dead（换一个缺口，回到 forming）
```
**硬规则**：连续修改 2–3 次仍未通过的，视为否决。不许绕过审稿直接写提案。

## 2. 各角色的执行标准

### 2.1 Gap Finder（对每个挑战轴各运行一次）
1. 使用该领域的**原术语**检索，至少 6 组 query；另外单独检索近 30 天的新论文。
2. 从结果里挑出最相关的论文，**读正文**，包括方法、主结果表和局限部分。
3. 输出 `## Axis: <轴名>`，下面分两节：
   - `### What has been done`：按机制归类已有做法，每条都要引用论文编号和具体机制，不能只写标题。
   - `### Open gaps`：**最多 2 个**缺口，每个都要按下面的格式写：
     - **Gap**：用一句对比句："已有方法用 Y 做 X，但 Y 的某个方法假设留下了问题 Z。"
     - **Near-miss**：至少 2 篇读过正文、离解决只差一步的论文，各自差在哪里。
     - **Methodological deficiency**：属于哪类方法缺陷（机制缺失、算法局限、归纳偏置错误、信用分配错误、目标不匹配、表示局限、规模局限），并给出正文证据。
     - **Why it matters**：谁因此被卡住，补上之后能解锁什么。
     - **Evidence route**：未来用什么可观测的证据证明缺口被补上了。**这里不写解决方案。**
4. 禁止：
   - 把 benchmark、数据集或"没人做过实验"包装成方法缺口；
   - 引用没读过正文的论文；
   - 把一篇论文自己的局限夸大成整个领域的缺口；
   - 仅凭"没人做过"就宣称有新颖性。

### 2.2 Innovator（每次只出一个直觉）
1. 先读 GAPS 和已有的 CANDIDATES。如果总控指定了"基于 C<x> 改进"，就保留原候选里有效的部分，只加强被指出的薄弱维度。
2. **寻找源机制**：至少 6 组检索，其中至少一半要**刻意跨领域**，覆盖 3 个以上不同的子领域，例如编码理论、信号处理、数据库与缓存、数值分析、在线学习、统计估计、编译器、操作系统。如果最合适的机制在本领域内，也可以用，但迁移不能只是简单重复。
3. **读源论文的正文**，确认两件事：机制是什么、它在源领域为什么有效；它成立所依赖的条件，在这里是否也成立。**最接近的同领域论文也必须读正文。**
4. 输出 `### C<n> — <短标题>`，下面分这几节：
   - **Intuition**：1–2 句话，外行能看懂
   - **Gap it attacks**：对应 GAPS 里的哪个缺口
   - **Source inspiration**：源论文编号、机制、为什么在源领域有效；并标注新颖性类型：新话题 / 远距离概念重组 / 加强弱联系
   - **How it maps**：什么对应什么（不写公式、不写伪代码）
   - **Why it could work**：成立的关键假设，以及源文献中支持它的证据
   - **Novelty vs closest**：最接近的论文编号，以及具体差别
   - **Main risk**：一句话
5. **导师追加的要求**（来自前几轮的失败教训）：
   - **成本账**：写出每个 token 的 FLOPs、HBM 字节数和额外工作区，对比当前最强的融合实现。按 H200 算：HBM 约 4.8 TB/s，BF16 dense 约 1 PFLOP/s。**账算不过来的直觉直接放弃**，不要交给审稿。
   - **比较对象要选对**：任何理论或经验主张，都必须和**最强的简单 baseline**（比如 RTN、FP8、随机淘汰）比较，**不能只和一个更弱的变体比**。上一轮被否的原因之一就是只和独立随机舍入比，没和 RTN 比。
   - **关键假设要有量级证据**：引用已发表论文里实测的量级。没有的话，就把"测量这个量级"列为第一个 kill test。

### 2.3 Reviewer（对抗审稿，每次只审一个候选）
默认立场是**怀疑**。必须**主动检索和阅读**，不能只看候选的描述就打分。逐项检查：
1. **源机制落地**：读源论文，核实候选对机制和适用条件的描述是否准确。
2. **新颖性（主动证伪）**：用"借来的机制 + 目标问题"组合关键词检索，加上近 30 天的新论文检索。疑似撞车的，读正文后再下结论。**资料包里列出的近邻必须逐一核对。**
3. **映射**：能否复述出"什么对应什么"。只有一个漂亮类比、却说不清对应关系的，要扣分。
4. **迁移可行性**：成立所需的关键条件是否写明了，在这里是否成立。
5. **贡献类型**：必须是方法。
6. **导师追加的检查**：
   - 成本账是否成立，是否和最强的融合实现比过；
   - 主张有没有选错比较对象；
   - 在最不利的场景下是否依然成立。在本 scope 里，这个场景是注意力集中的检索头、只出现一次的事实，以及 AIME 这类难题。
7. 输出 `### C<n> verdict`：
   - **Verdict**：`survive` / `revise(focus=novelty|coherence|feasibility|clarity|mapping|grounding)` / `reject(reason=...)`
   - **Evidence**：逐条列出，每条附论文编号和 1–2 句理由
   - **Strongest objection**：一句话

### 2.4 Report Writer（只给 survive 的候选写）
输出一个**合法的 JSON 对象**，字段包括：
- `title`、`one_sentence_thesis`（不超过 30 词）
- `core_problem`：`problem_statement`、`why_it_matters`、`concrete_example`
- `key_novelty`：`main_idea`、`explanation`
- `problem_definition`、`key_terms`
- `related_work`：列表，每项含 `sub_area`、`what_it_does`、`open_gap`、`citations`
- `method`：`high_level_flow`、`modules`、`design_choices`、`theoretical_grounding`
- `model_details`：基座模型、训练方式或"无训练"
- `comparison_to_sota`
- `proposed_evaluation`：`benchmarks`、`baselines`、`main_metrics`、`ablations`
- `falsifiable_predictions`：列表，每项含 `pillar`、`prediction`、`kill_condition`
- `limitations`

**每个字段都要填写。不许编造实验结果**，预测必须标明是预测。引用只能用读过正文的论文。

### 2.5 模拟评审组（提案写完后进行）
- **R1 领域专家**：专门找撞车和缺失的 baseline。
- **R2 外行资深审稿人**：判断问题是否重要、洞见是否清晰、故事是否讲得通。
- **R3 实验派**：判断实验能否说服人、baseline 是否公平、消融是否能隔离出机制的作用、预算够不够。

**评审设定**：每位评审**只看 REPORT 和资料包里的约束**，假设实验完全按计划执行，并且每条预测**恰好达到门槛**（不会更好），每人**自己再做至少 6 组检索**，然后输出：
- 优点；
- 缺点，标注为致命 / 严重 / 轻微；
- 重叠的已有工作；
- 缺失的 baseline；
- 评分 1–6；
- p_core，即核心预测真正成立的概率；
- 一处改动就能加一分的地方。

**AC** 读完三份评审后给出：
- `odds`：录用把握，按十分之一计；
- `p_core`；
- `odds_risk_adjusted`；
- `decisive_weaknesses`；
- `fixes_ranked`。

AC 的校准锚点：
- 主会录用率约 24%，普通投稿约 2.5/10；
- 有未解决的致命问题，最多 1.5；
- 3/3/3 对应 1–2；
- 4/3/3 对应 3–4；
- 4/4/4 且没有未解决的严重问题，对应 5–6；
- 5/4/4 及以上，对应 7–8。

如果 odds < 5，就把 `fixes_ranked` 作为修改重点，让 Report Writer 或 Innovator 修改后重新评审。**最多修改 2 轮。**

## 4. 导师在本 scope 上的具体指导（资料包里有详细依据）

- **优先方向**：在 **1.25–2.5 bit** 区间，把长 CoT **难题上的准确率**补回来，并且按**每答对一题的成本**评估。这个指标要和 FP8/FP4 在显存打满的条件下比。TaSQ 在 1.25 bit 下 AIME25 掉了 17.8 分，NIAH 64K 掉了 14 分，这是目前最清楚、有实测量级的缺口。
- **值得重点考虑**：按头、按角色或按 token 自适应分配精度，例如检索头用高精度、注意力分散的头压到极低比特。动手前要先和 DuoAttention、TaSQ、ThinKV、MiKV、KVTuner、MultiAlloc 等工作区分清楚，完整的近邻列表见资料包。
- **不推荐作为主要动机**："KV 量化导致推理变长"。TaSQ 和 KVarN 测到的长度都接近 BF16。除非你能找到相反的实测证据。
- **已经被否、不要重提的方向**：见资料包的被否清单，每一条都附有死因。
- **评测协议**：严格按资料包执行。所有方法在相同字节数下比较（元数据、窗口、保护层都要计入）；AIME 至少 avg@16；报告生成长度、循环率和撞上限率；在显存打满的条件下报告每答对一题的墙钟时间；不要求两条轨迹逐 token 一致。

**全程要求：不编造，不跳步，在检查点停下来汇报。**

## 1. Scope 与成功标准

- **问题**：长思维链生成 16K–64K token 时，在解码阶段压缩 KV cache。目标是在**显存打满的真实服务条件下**，让每**答对一题**的墙钟时间和每个请求的显存都下降。
- **只有下面 6 条全部满足才算成功**：
  1. 准确率没有统计显著的下降；
  2. 生成长度没有实质膨胀；
  3. 循环率和撞长度上限率没有上升；
  4. KV 实际占用的字节数下降，元数据要算进去；
  5. 显存打满时能承载的 batch 变大；
  6. 每答对一题的墙钟时间下降，并且要**优于 FP8/FP4 KV**。

  只改善 MSE、注意力 KL 或单个 kernel 的耗时，不算成功。
- **约束**：H200 共约 1 TB 显存；执行者是新手学生，有组内 kernel 工程师支持；目标会议 NeurIPS / ICML / ICLR / MLSys。

## 4. 建议的挑战轴（供 Gap Finder 使用）
1. **超低比特（1.25–2.5 bit）下难题与长距检索的准确率损失**：TaSQ、AsymKV、KVarN 的掉分集中在哪里，是哪些头、哪些 token、哪些推理阶段。
2. **在线、按头或按角色的 K/V 精度分配**：现有分配都是离线静态的（KVTuner、MultiAlloc），或者按 token 预算而不是按精度分配（DuoAttention）。

# 第三部分　种子方向

总体判断：在长 CoT 的 KV 压缩里，**还空着的地方不在"做一个更好的量化器"，而在"按注意力的实际读取方式，把精度分配到误差真正会放大的地方"**。TaSQ（1.25 bit）的长度控制得不错，但难题掉了 17.8 分、64K 的 NIAH 掉了 14 分，说明它在少数关键读取上丢了精度。下面 4 个种子都从这一点出发。

---

## 种子一（首选）：K 和 V 对注意力集中度的敏感方向相反，按头或按块做非对称精度分配

**一句话**：K 的量化误差在注意力**分散**时危害最大，V 的量化误差在注意力**集中**时危害最大，所以同一个头的 K、V 比特预算应该朝相反方向调。

**初步推导（需要 GPT 严格化）**：
- **V 侧**：设各 token 的 V 量化误差独立，方差为 σ_i²。读出误差满足 E‖Σ_i p_i e_i‖² = Σ_i p_i² σ_i²。在等方差时，这等于 σ²·Σp² = σ²/n_eff，其中 n_eff = 1/Σp² 是注意力的有效样本数。也就是说，**注意力越集中（n_eff 越小），V 误差越不会被平均掉**。这和 C2 审稿中的数值结果一致：一个 token 占 0.9 权重时，V1 比 V2 差约 23 倍。
- **K 侧**：分数误差 δs_i = q·δk_i/√d。在二阶近似下，前向 KL ≈ ½·Var_p(δs)，误差独立时其期望为 ½·Σ_i p_i(1−p_i)·σ_{s,i}²。在 |q| 固定的条件下，注意力越集中（某个 p_j→1），这个量越小，所以 **K 误差在分散注意力下危害更大**。
- **反例和难点**：我的合成实验（导师用合成数据做过的检验）中，尖锐注意力下 K 的 KL 反而更大。原因是实验里用放大 |q| 来让注意力变尖锐，而 |q| 变大同时也放大了 δs。所以真正的问题是：**注意力集中这件事，是来自分数差距大（对 K 误差稳健），还是来自 |q| 大（会放大 K 误差）？** 需要把两者分开推导，并给出超出二阶近似、分数差距和扰动同量级时的结论。

**请 GPT 完成**：
1. 严格推导 K 误差和 V 误差对注意力输出的影响，用注意力分布的统计量表示，例如 n_eff、Var_p、top-1 与 top-2 的分数差、|q| 的分布。给出二阶近似成立的条件，以及不成立时的界。
2. 处理实际结构：
   - GQA 中一个 KV 头被多个 query 头共享，敏感度要对组内的 query 头聚合；
   - RoPE 的影响；
   - KV 存一次、会被后续成千上万步反复读取，所以敏感度要对"未来的查询分布"求期望，而不是只看当前一步。
3. 在总字节预算约束下，求每个头（或每个块）K、V 比特的最优分配。预期形式是 water-filling：b_h^K ∝ ½·log₂(K 敏感度)，b_h^V ∝ ½·log₂(V 敏感度)。要给出闭式解或近似解。
4. 设计在线估计：敏感度统计量能否从**已经算过的注意力**里免费得到（例如上一步的 Σp²），并说明估计误差对分配结果的影响。
5. V 在注意力分散的头上可以压到 V1，配合确定性误差扩散（sigma-delta / 保持块和），对应 C2 审稿留下的挽救方向。要推导它和 RTN 相比的误差界。

**依据**：
- TaSQ 的难题掉分和 NIAH 掉分 [2610.03027]；
- 检索头稀疏，但屏蔽后 CoT 会崩 [2404.15574]；
- DuoAttention 对检索头保留全量 KV [2410.10819]；
- 63–85% 的头会在生成过程中改变自己看哪里，所以静态分类不可靠 [2610.02713]。

**已知近邻（必须正面区分）**：DuoAttention、RazorAttention、HeadKV（按头分配 token 预算，而不是精度）；KVTuner、MultiAlloc（离线的逐层精度）；MiKV、ZipCache（按 token 重要性分配混合精度）；ThinKV（按思维类型分配）；TaSQ（query 引导的通道加权）。**预期差异点**：用"K 和 V 对集中度方向相反"这一条理论来**同时**决定两者的精度，并且在线进行。这个说法是否已有人提出，**待查新**。

**一周 kill test**：在 Qwen3-8B 和 Qwen3-4B-Thinking 上抓取真实的注意力分布和 KV，按头测量"K 误差的注意力 KL"和"V 误差的读出误差"随 n_eff 变化的关系。如果两者的相关方向**不相反**，或者按头的差异很小（例如在相同字节下，最优分配比均匀分配的输出误差降低不到 20%），就放弃。

## 种子二：按请求难度做精度准入与升级（服务层的整体优化）

**一句话**：简单题用低比特、难题用高比特，按"每秒答对题数"最大化，在线决定每个请求的 KV 精度和 batch 组成。

**依据**：
- TaSQ 在 AIME24 上掉 5.5 分、在 AIME25 上掉 17.8 分，说明低比特带来的损失**集中在难题上**；
- 在显存打满时，比特数直接决定 batch 大小，从而决定吞吐 [2610.03027, 2606.20474]；
- 2606.02011 发现，2-bit（权重）量化的退化按"题目难度区间"分化，并且可以用早期信号识别。

**请 GPT 完成**：
1. 建立优化模型：在显存约束下，选择每个请求的精度 b_r（可在生成中途升级），最大化期望的"答对题数 / 秒"。推导最优策略的结构，例如阈值策略：难度信号超过 τ(b, 负载) 就升级。
2. 精度升级的代价：已经写入的低比特 KV，是保留、重新量化，还是从 CPU 上的高精度副本取回？分别给出代价模型。
3. 难度信号用什么：早期 token 熵、已生成长度、反思词频率、草稿接受率（与 scout C 的 P4 相关）。说明每种信号在什么条件下能预测"低比特会答错"。
4. 推导该策略相对"固定 FP8"和"固定 1.25 bit"的收益条件。

**已知近邻**：按请求的思考预算 / 路由（OTBench [2610.13570] 中的各种 router）；2606.02011 的 FP16 回退（针对权重量化，需要整条从头重跑）；推理服务的调度工作（PASCAL 等，不涉及精度）。**待查新**：是否已有工作做"按请求选择 KV 精度"。

**一周 kill test**：离线跑 Qwen3-4B-Thinking，在 FP8、2 bit、1.25 bit 下各采样 AIME 和 MATH-500，计算一个**理想上界**：假设能提前知道每道题在哪个精度下答对，按题分配精度能把每题成本降多少。如果这个上界相对"固定最优精度"的提升不到 15%，就放弃。

## 种子三：KV 量化误差在长程解码中的传播，作为端到端可信的分配指标

**一句话**：用一个能刻画"写入一次、被读取几万次"的误差传播模型，取代离线失真曲线，作为比特分配的依据。

**依据**：
- 离线失真曲线在 3 个模型里有 2 个选错了比特宽 [2610.05685]；
- OSCAR 的最优性只在"冻结误差"假设下成立 [2605.17757 App D]；
- 逐步计算的界很保守，单层误差本身并不致命 [2607.28699]。

**请 GPT 完成**：
1. 把 KV 误差在后续每一步、每一层中的传播线性化：通过注意力 Jacobian 和残差流逐步传递，推导出某个 token 在某个头上的 KV 误差，对未来 T 步输出分布的累计影响（KL 或 logit 方差）的表达式。
2. 化简出可以在线计算的近似量，例如"未来期望注意力质量 × 敏感度"。注意它和 ForesightKV、KVP 这类"预测未来注意力"的淘汰方法的区别：这里预测的是**误差放大**，不是**是否保留**。
3. 证明或否证：这个指标给出的比特排序，是否能正确预测 2610.05685 中观察到的那种"离线选 4 bit、端到端最优是 2 bit"的反转。

**已知近邻**：KVTuner、PM-KVQ、MultiAlloc、KVarN 的 pseudo-decode 协议、ForesightKV、KVP。**风险**：推导出来的量可能太贵，在线算不起，或者最后退化成"累计注意力"这类已有指标。

**一周 kill test**：在 3 个模型上，用这个指标做离线分配，复现 2610.05685 的设定。如果它预测正确的比例不比失真曲线高，就放弃。

## 种子四（高风险）：读取时按注意力集中度，从 CPU 回取残差位平面

**一句话**：KV 在 HBM 中常驻 1.25 bit 的基础码，高精度残差放在 CPU。每一步只对**注意力高度集中的少数块**回取残差，用来做精确读取。

**依据**：
- 种子一推导出的 V 误差 ∝ Σp²，意味着只有少数块需要精确值；
- 精确卸载不伤准确率 [2605.09490]；
- HiSparse 的回取命中率达到 87% [2608.07009]；
- 现有的升降级策略按累计注意力触发 [2608.05326]，证书方法在 1–2 bit 下是空洞的 [2607.28699]。

**请 GPT 完成**：
1. 只用基础码推导"该块残差对输出的影响上界或期望"，作为回取的触发条件。需要在 1–2 bit 下仍然**有效**，不能像 WitCert 那样变成空洞的界。可以考虑用期望界或概率界代替最坏情况界。
2. 建立回取量、PCIe 带宽和延迟的代价模型，给出收益为正的条件，包括 batch、长度和集中度的取值范围。

**已知近邻（拥挤，需要逐一区分）**：Read What Matters（按 query 读取比特）、QEvict、WitCert、HiSparse、VeriCache、Not All Thoughts Need HBM。**风险**：很可能已有人做过，查新优先级最高。
