# P0 实验操作手册（学生版）

> 本手册讲清楚 P0 的完整操作流程，供学生在 H200 上执行时参照。
> **具体的脚本名、参数名以 GPT 交付的代码包为准**（`p0/README.md`）。下面的命令只是示意，用来说明每一步在做什么。导师审完代码包后，会按实际脚本名更新本手册。
> 已确认存在的接口：SGLang 的 `--kv-cache-dtype`、`/generate` 接口中的 `input_ids` / `return_logprob` / `top_logprobs_num`，以及 vLLM 的 `--kv-cache-dtype fp8`。INT2 档用的是 OptR fork 自带的选项。

---

## 0. 准备工作（约半天）

### 硬件
8×H200。P0 不需要多卡并行推理：8B 模型一张卡就放得下，所以每张卡起一个独立的推理服务，8 个服务并行跑不同的题目或样本。

### 软件
1. 拉取 OptR 的 SGLang fork，切换到 GPT 代码包里写定的 commit，按它的 README 安装。
2. 另建一个环境，安装 vLLM，只用来做原生 FP8 校验。
3. 下载两个模型：`Qwen/Qwen3-8B`、`Qwen/Qwen3-4B-Thinking-2507`。
4. 把 P0 代码包放到工作目录，记下它的 git commit 号。所有结果都要标注这个 commit 号。

### 数据
`aime_2024_2025.jsonl`，共 60 行，每行包含题号、题目和标准答案。代码包里已经提供，并已校验过。

### 习惯
- 所有长时间任务都在 `tmux` 里跑，断网也不会中断。
- 所有输出都是"追加写入"的 JSONL，脚本启动时会跳过已完成的样本。中途挂掉的话，直接重跑同一条命令即可续上。
- top-20 logprob 的数据量比较大，S1 全部跑完约十几到几十 GB，保存时用压缩格式。先确认磁盘空间足够。

## 1. 一致性检查（约 1 小时，必须第一个做）

**目的**：确认"把 token id 交给引擎重新 prefill"这一步不会改变模型看到的内容。后面所有的"中途升级"都依赖这一步。

**做法**：
1. 用 BF16 服务生成一条完整轨迹，保存 token id 和每步的 logprob。
2. 在这条轨迹上取几个位置（比如第 1K、4K、8K 个 token），把"题目 + 到这个位置为止的 token id"作为 `input_ids` 重新提交给**同一个 BF16 服务**，只生成 1 个 token，返回 top-20 logprob。
3. 对比重新 prefill 后的下一个 token 分布和原轨迹在同一位置的分布。

**通过标准**：top-1 一致，KL 接近 0。不通过就**停下来**，把输出发给导师。最常见的原因是不小心重新套了 chat template，或者 `<think>` 标签被处理过。

请求示意：
```json
POST /generate
{
  "input_ids": [151644, 872, ..., 1234],
  "sampling_params": {"max_new_tokens": 1, "temperature": 0},
  "return_logprob": true,
  "top_logprobs_num": 20
}
```

## 2. S0：长度校准（几个 GPU 小时）

**目的**：选一个足够大的生成上限，保证 BF16 本身很少写满上限。否则分不清是"失控"还是"上限太短"。

**做法**：
1. 每个模型起 BF16 服务，上限设为 81,920。
2. 60 题每题生成 2 次：temperature 0.6，top-p 0.95，种子固定。
3. 统计长度分布：平均值、中位数、90 分位、最大值，以及在 32K、48K、64K、80K 各个上限下会被截断的比例。
4. 同时记下实测吞吐（token/s），用于重算后面的时间预算。

**产出（发给导师）**：每个模型的长度分布表、建议的上限（取让 BF16 截断比例 ≤ 10% 的最小一档），以及实测吞吐。导师确认后再进入 S1。

## 3. S1：主采样（约一天，视长度而定）

### 3.1 要跑什么
对每个模型，依次用三种 KV 精度起服务：BF16、FP8、INT2（OSCAR+OptR）。每种精度下 60 题、每题 16 次，上限用 S0 定下的值。

| 模型 | 精度 | 题数 × 次数 | 轨迹数 |
|---|---|---|---|
| Qwen3-8B | BF16、FP8、INT2 | 60 × 16 | 2,880 |
| Qwen3-4B-Thinking-2507 | BF16、FP8、INT2 | 60 × 16 | 2,880 |
| 校验：vLLM 原生 FP8 | 两个模型 | 60 × 4 | 480 |

8 张卡的分配：同一时间所有卡跑同一个"模型 + 精度"组合，8 个服务分摊 960 条轨迹，跑完再换下一个组合。这样不同精度之间不会互相干扰。

### 3.2 每条轨迹保存什么
一条轨迹对应一条 JSONL 记录，示意如下：
```json
{
  "model": "Qwen3-8B", "kv": "int2", "qid": "2025-I-07", "sample": 3, "seed": 1003,
  "code_commit": "abc1234", "engine_commit": "def5678",
  "prompt_ids": [...], "output_ids": [...],
  "token_logprob": [...], "top20": "存在单独的压缩文件里，这里只记文件名和偏移",
  "length": 41237, "hit_cap": false, "think_closed": true,
  "pred_answer": "204", "correct": true
}
```

### 3.3 判分
1. 取最后一个 `\boxed{...}` 里的内容作为预测答案。AIME 答案都是 0–999 的整数，规范化成整数后和标准答案比较。
2. 没有 `\boxed`、思考未结束、写满上限的，一律判错。同时分别标记原因，后面要用。
3. 判分脚本先在 BF16 的结果上抽查 20 条，人工确认判分正确。

### 3.4 S1 跑完后算什么（分析脚本一键生成）

**Q1 救援空间**：每题分别算 FP8 和 INT2 的准确率，相减后对 60 题取平均，并给出按题 bootstrap 的置信区间。两个模型都要报，FP8 和 BF16 两种口径都要报。

**Q2 成本集中**：在 INT2 轨迹里：
- 先按 2606.02011 的 n-gram 定义标出"打转"的轨迹；
- 算出"打转或写满上限"的轨迹占总显存-时间（∝ 长度²）的比例，再除以它们占轨迹数的比例；
- 画洛伦兹曲线。

**Q3 早期可预测**：
- 对每条 INT2 轨迹，只用前 2K、4K、8K 个 token 计算特征：熵的均值和趋势、n-gram 重复率、反思词频率、自相似度、思考是否结束；
- 标签是"最终答错或写满上限"；
- 用逻辑回归，**按题目分组**做交叉验证（同一题的样本不能同时出现在训练集和测试集），报告 AUC 和置信区间。

**vLLM FP8 校验**：比较 fork 里的 FP8 和 vLLM 原生 FP8 的准确率与平均长度。如果 fork 的 FP8 低 5 个百分点以上，或者平均长度多 10% 以上，Q1 和 Q4 改用 BF16 口径。

### 3.5 闸门（导师判定）
把分析报告发给导师。如果 Q1 在两个模型、两种口径下都低于 5 个百分点，**不跑 S2**，P0 到此结束。

## 4. S2：分叉实验（约一天，视失败轨迹数量而定）

### 4.1 选样本
抽样脚本在 S1 开始前就已经固定并提交，种子和规则不能改：
- 每个模型从 INT2 的失败轨迹（答错或写满上限）中抽至多 60 条，每题至多 3 条，按题分层；
- 另抽 50 条 INT2 下答对的轨迹作对照。

### 4.2 切点和分支
每条选中的轨迹，在第 4K、8K、16K 个 token 处切开（超过轨迹实际长度的切点跳过）。每个切点跑以下分支，每个分支 4 次，每次换一个随机种子：

| 分支 | 交给哪个服务 | 输入 |
|---|---|---|
| H 续写（FP8） | FP8 服务 | 题目 + 前 t 个 token 的 id |
| H 续写（BF16） | BF16 服务 | 同上 |
| L 续写 | INT2 服务 | 同上 |
| H 重开 | FP8 服务 | 只有题目 |
| L 重开 | INT2 服务 | 只有题目 |

- 重开和切点无关，同一条源轨迹只跑一组，所有切点共用，计费时去重。
- 对照组（50 条答对的轨迹）只跑 H 续写和 L 续写。

续写请求示意：
```json
POST /generate
{
  "input_ids": ["题目的 token id", "……", "原轨迹前 8192 个 token 的 id"],
  "sampling_params": {"max_new_tokens": "上限 - 已有长度", "temperature": 0.6, "top_p": 0.95, "seed": 20001},
  "return_logprob": true, "top_logprobs_num": 20
}
```

### 4.3 判分与计算
每个分支的续写同样判分。然后计算：
- **恢复率**：原本失败的轨迹，在这个分支下最终答对的比例。
- **精度的功劳**：H 续写 − L 续写。主分层是 Qwen3-8B、8K 切点、FP8 口径：差值 ≥ 10 个百分点，且置信区间下界 > 0，才算机制成立。其余分层做 Holm 校正，只作探索性结果。
- **中途接续 vs 重开**：比较 H 续写和 H 重开的恢复率，以及各自额外花了多少 token。差值的置信区间完全落在 ±5 个百分点内，判为"相当"。
- **误升级的代价**：对照组在 H 续写后准确率是否下降。
- **什么时候救最有效**：画恢复率随切点位置变化的曲线。

## 5. 时间与交付

| 步骤 | 预计耗时（8×H200） | 交给导师的东西 |
|---|---|---|
| 准备 + 一致性检查 | 半天到一天 | 一致性检查的结果 |
| S0 | 几个小时 | 长度分布、建议上限、实测吞吐 |
| S1 | 约一天 | Q1–Q3 的分析报告、vLLM FP8 校验结果 |
| S2 | 约一天 | Q4 的分析报告 |

实际耗时取决于 S0 测出的平均长度和吞吐。S0 跑完后，导师会重算一次时间预算。

**每次交付都附上**：代码 commit 号、引擎 commit 号、运行命令、报错或异常的日志。不要手动修改任何结果文件，有问题就重跑。
