# What Matters in Orchestrating Robot Policies: A Systematic Study of Hierarchical VLA Agents

## What this paper does
Casts hierarchical VLA (Hi-VLA) agents as an options-style loop: a high-level VLM option selector pi_VLM(l | mem(phi(o)), I), a low-level VLA intra-option policy, a termination condition beta, a memory module and an observation-representation module (Alg 1). It varies one component at a time in MuJoCo ALOHA (short-horizon, long-horizon, reasoning tasks) with Gemini 2.5 Lite/Flash/Pro planners and Gemini Robotics On-Device VLAs, then validates on a second stack and a real ALOHA robot.

## Goal-by-goal answers
### Goal: How does a Hi-VLA controller track task state and decide when a sub-task is done?
Termination options compared: fixed frequency, success detector, VLM-predicted execution time [full text, Sec 4.4]. The success detector is implemented "by querying a VLM with privileged state of the simulator to make it as accurate as possible" [Sec 4.4, App F], so no image-only completion judge is evaluated. Success detection performs best; VLM-predicted time is worst because VLA execution length is stochastic [Sec 4.4]. State is supplied by memory windows (1, 3, 5 steps, full episode) or text summaries [Sec 4.6].
### Goal: What does it find about in-episode memory and observation representation for the controller?
History length "doesn't affect the performance much", suggesting the VLM "cannot extract useful information from raw history"; in-episode summarization is "neutral to negative"; only cross-episode summaries help [Sec 4.6]. Converting images to text with VLM bounding boxes, or with privileged contact info from the simulator, "significantly boost[s] performance" over raw images, explained by VLMs ignoring image inputs as tasks get harder [Sec 4.5].
### Goal: How sensitive is the system to success-detector errors, and what assumption limits that result?
Injected false positives at 30-50% "drastically impact the system performance" because the false "command completed" makes the VLM move on; false negatives hurt moderately [App C, Fig 5]. The authors flag that their corruption is independent across states, whereas a real detector's errors are correlated across consecutive states, so one FN can stall a command for a long time [App C].
### Goal: What does it say about controller size and adaptation?
With thinking on, Gemini Lite, Flash and Pro perform similarly; thinking matters more than size, especially on long-horizon tasks [Sec 4.2]. Fine-tuning the VLA in-domain hurt instruction following and system success [Sec 4.3]. Future work: RL or SFT of the high-level VLM on cross-episodic experience [Sec 4.6, Sec 5]. No open <=8B VLM controller is tested.

# What Matters in Orchestrating Robot Policies: A Systematic Study of Hierarchical VLA Agents

## What this paper does
The paper casts hierarchical VLA agents as an options framework (high-level VLM selects language option l, VLA executes, termination condition beta returns control) and runs controlled ablations of the high-level VLM (Gemini 2.5 Lite/Flash/Pro, thinking on/off), low-level VLA (Gemini Robotics On-Device variants), termination (fixed frequency, success detector, VLM-predicted duration), observation representation (raw image, summaries, bounding boxes, privileged contact) and memory, on MuJoCo ALOHA short/long-horizon/reasoning tasks and a real ALOHA.

## Goal-by-goal answers
### Goal: Which controller components matter most, and does controller size matter?
Thinking consistently helps, more on long-horizon tasks; VLM size (Lite vs Flash vs Pro, thinking on) "does not have a significant impact" [full text, Sec 4.2]. Raw-history memory length barely matters: "the VLM cannot extract useful information from raw history of current episode" [Sec 4.6]. Text summaries with bounding boxes or privileged contact info significantly beat raw images, attributed to VLMs ignoring images as tasks get harder [Sec 4.5].
### Goal: How is sub-task completion (termination) judged, and how sensitive is the system to it?
The best termination is a success detector implemented by "querying a VLM with privileged state of the simulator"; VLM-predicted execution time is worst due to VLA stochasticity [Sec 4.4]. The system is robust to moderate detector error but "too high of a detection error will significantly impact its performance" [Sec 4.4, App C].
### Goal: Is any learning/distillation of the controller studied?
No; all high-level VLMs are prompted Gemini models without fine-tuning. Fine-tuning the VLA on in-domain sim data hurt hierarchical performance because it reduced steerability to rephrased instructions [Sec 4.3].
