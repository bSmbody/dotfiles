# DynamicVLA: A Vision-Language-Action Model for Dynamic Object Manipulation

## What this paper does
A compact VLA for moving-object manipulation with a temporal observation window, a greedy continuous inference schedule (next inference launched as soon as the previous ends, newer chunks override overlapping older actions), and Latency-aware Action Streaming; introduces the DOM benchmark (sim + real) for dynamic manipulation. NeurIPS 2026.

## Goal-by-goal answers

### Goal: What mechanism maps a delayed high-level decision/observation onto the current state?
Latency-aware Action Streaming: a chunk predicted from O_t arrives at t+m; the prefix {a_t..a_{t+m-1}} is "indexed to execution times that have elapsed", so it is discarded and only the suffix {a_{t+m}..a_{t+n}} is streamed [full text, Section 3.4]. Compensation relies on the policy having already predicted actions for times beyond the delay.

### Goal: What does the method assume about the slow decision-maker (trainable, white-box features, output type, delay scale)?
The decision-maker is the trained VLA itself, outputting time-indexed continuous action chunks, with inference delay m shorter than the chunk length n [Sections 3.3-3.4].

### Goal: What does it report as a limitation relevant to this axis?
Authors name the "fundamental tension between semantic understanding and real-time responsiveness" and call for faster VLAs; longer-horizon multi-stage dynamic tasks and richer dynamics are future work [Section 6]. A discrete, non-time-indexed decision has no valid suffix to stream, so the mechanism does not apply to it.


### Goal: Which DOM sub-dimensions require choosing among several moving objects or reacting to multimodal motion, and what executor does DOM provide?
DOM has nine sub-dimensions in three groups [full text, Sec 4.2]: Interaction = closed-loop reactivity (CR), dynamic adaptation (DA: "abrupt motion changes such as direction shifts or unexpected disturbances"), long-horizon sequencing (LS: "prioritizes actions as motion events unfold"); Perception = visual understanding (VU), spatial reasoning (SR), motion perception (MP: targets specified by speed/direction); Generalization = visual, motion, disturbance robustness. "Multiple objects are placed in the workspace"; speeds 0–1 m/s (training 0.15–0.75 m/s), friction 0.5–1.5; Isaac Sim, Franka, three 25 FPS cameras [Sec 4.3]. Each sub-dimension: 10 test environments × 20 trials with pre-generated poses, velocities and scripted disturbance events, specifications shipped with the release [Appendix D]. Real-world task specs include multi-object perception ("tennis ball among multiple simultaneously thrown objects", "the slower ball", "the faster-rolling can"), collision-deflected trajectories, and objects that "repeatedly appear" to be gathered [Appendix D]. DOM's automatic demonstrator consumes real-time object pose and velocity plus target pose, "predicts short-horizon object motion during approach, continuously updates the end-effector target", and runs approach / grasp-and-lift / place / reset [Sec 4.3]; it is a ready-made scripted intercept executor. Prior VLAs score low on DA and LS; DynamicVLA reaches 38.5% (DA) and 40.5% (LS) [Sec 5.2]. All DOM latencies are sub-second (0.226 s per chunk) [Sec 5.1], so DOM speeds are calibrated for VLA latency, not multi-second brain calls.


### Goal: When are DOM's instruction referents fixed, which forks are exogenous vs deterministic, and are the evaluator and demonstrator released and non-paused?
Paper: instructions are "generated from attribute tags (appearance, size, spatial position, distance, and speed) ranked by per-episode object states"; per-trial initial poses, velocities and friction are pre-generated and "reused identically across all methods", and disturbance events are "scripted per trial"; Disturbance Robustness "applies scripted pushes and collisions at evaluation time only" [full text, App D]. Metrics are success and task completion time from motion onset [Sec 5.1]. Released code (github hzxie/DynamicVLA, "Released training and testing code" 2026-04-26), read directly: `simulate.py` computes the tags once from the initial `object_states` when the environment is built, and for the long-horizon task the tag is "entire set of objects", with the demonstrator taking the fastest remaining object next (`get_next_object`, argmax speed). So the referent of a single-object instruction is fixed at t0, and long-horizon order carries no instruction semantics. Exogenous events are the optional force/torque `perturbation` events and the scripted DR pushes. Straight, curved and collision-deflected rolls come from the physics engine and are deterministic given the initial state. `evaluate.py` is non-paused by design: it reads actions with a non-blocking ZMQ receive, holds the last action (initially the home pose) when none has arrived, and paces each step to wall-clock `step_dt`. The automatic demonstrator is released as Warp state machines (`simulations/state_machines/pick_sm.py`, `place_sm.py`): it tracks the live object pose and velocity, and gates only on the current end-effector-to-object distance against `max_reach_dist` (0.75 m for Franka), resetting when the object leaves reach. It does not compute future interception windows. `sim_cfg.yaml` sets speeds [0.15, 0.75] m/s, with a commented alternative [0.05, 0.25], and episode lengths of 10 s (pick), 12 s (place) and 20 s (long-horizon).
