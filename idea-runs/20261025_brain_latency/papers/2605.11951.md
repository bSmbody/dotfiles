# From Reaction to Anticipation: Proactive Failure Recovery through Agentic Task Graph for Robotic Manipulation (AgentChord)

## What this paper does
AgentChord (RSS 2026) uses GPT-5-backed agents to turn an instruction plus the initial observation o_0 into a directed task graph (nodes = sub-goals with constraints c(z)<=0, edges = constrained motion transitions), then a recovery-orchestration agent predicts likely failure modes per edge, writes each as a scalar monitor f_m(z_t) over geometric/gripper features, and attaches forward-moving recovery nodes/edges that merge back into the nominal graph. A compilation agent turns all edges into receding-horizon solver programs. Online, monitors with a margin and persistence window trigger the pre-compiled recovery edge "without re-invoking full task planning". Evaluated on 3 EmbodiChain sim tasks and 6 real bimanual tasks with injected disturbances against IM, DoReMi, ReKep, CaM.

## Goal-by-goal answers
### Goal: Does the brain pre-specify monitors and local recoveries that fire without re-calling the brain, and how are they parameterized?
Yes — this is the closest prior work to the axis. Before execution, PredictFailures is called once per nominal edge on (I, o_0, G) (Algorithm 1, lines 5–8) and emits failure modes, each "paired with an online-detectable trigger and a recovery intent (re-align, re-approach, re-grasp)" [full text, Sec. III-C]. Monitors are scalar functions over z_t = Φ(x̂_t, ξ_t): object shift ||p_t − p̄|| − δ_shift with p̄ "taken from the last stable estimate at node v^i or from the expected in-hand pose", tilt vs gravity, gripper width g_t − g_th, object–gripper attachment distance, point-count visibility, relational offset [full text, App. C-G, Eqs. 14–19]. Trigger fires when violation > ε persists K steps (Eq. 12); execution switches to ρ(edge, f_m) (Eq. 13). Recovery edges are re-solved online by the receding-horizon solver from the latest perception (Eq. 10), so the recovery *intent* is pre-armed but its geometry is closed-loop. Tolerances: "we use shared default settings rather than task-specific tuning", optionally adjusted by the MLLM at compile time [App. C-G]. The entire graph and all branches are generated once from o_0; there is no per-stage re-arming as the task progresses.

### Goal: Does it measure wall-clock latency/time saved by avoiding brain re-calls, and does the world keep evolving (no pause) during brain calls?
It reports execution time "from the moment the system receives the initial inputs ... until the task is completed", which "captures the full system latency, encompassing perception, planning, action execution, and all MLLM inference costs" [Sec. IV-A]. Real-world averages (ablation Table V): AgentChord 105.6 s vs backtracking variant 128.4 s vs ReKep 122.4 s; CaM's longer time is attributed to "repeatedly invoking an MLLM upon sub-task completion or failure detection" [Sec. IV-B/IV-C]. So time saved by not re-calling the brain is measured, but only as a sum of serial costs: disturbances are discrete events (object drop with probability p, object pushed/removed by hand) in otherwise static scenes, and nothing in the text says the scene evolves during an MLLM call or that latency was varied as an independent variable. The paper never models what happens to the world while the upfront graph synthesis runs, and monitors use a static reference p̄, so steady object motion (conveyor, moving target) would read as "shift" failure.

### Goal: What limitation does it report on recovery/monitoring?
(i) Failure modes not anticipated during graph construction are not covered; the suggested fallback is to re-invoke the MLLM pipeline at sub-goal boundaries or timeout [Sec. V]. (ii) The compilation agent sometimes picks the wrong monitor signal (object–gripper distance instead of gripper aperture for "securely held") [Sec. IV-D]. (iii) IK infeasibility of recovery intents (re-grasping a tipped block) [Sec. IV-D]. (iv) Features like PCA orientation unreliable for deformable/transparent objects [Sec. V].
