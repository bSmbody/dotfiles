### C1 verdict

- **Verdict**: revise(focus=novelty)
- **Evidence**:
  - **Source grounding: mostly accurate, with two overreaches.**
    - [2010.05486]: the split is stated correctly. The controller acts on the delay-free model output, the measurement corrects only mismatch, and the nominal delay leaves the characteristic equation (Sec II, Eq 10). But "timestamping doubles the tolerable variable delay" comes from one numerical example (4 vs 2 samples, Sec IV-B), not a general result. The predictor also assumes a known linear plant and a continuous command. C1 borrows the decide-on-model / act-on-measurement split, not any guarantee.
    - [1809.08627]: correct. Only the robot's own tools are predicted, from commands already sent. The 1 s delay task got 19% faster (60.6 vs 49.2 s), with no significant change in errors. The environment is explicitly left unpredicted.
    - [2310.11441]: overstretched as the "enabler". SoM moves marks "off the region slightly" only for very small regions (Sec 2.3), and reports misattribution of nearby or overlapping marks (Sec 4.4). A ghost drawn 20 cm away from an object that is still visible is a different regime from anything SoM tested. Whether a frontier model reliably links ghost k to the object it belongs to is an untested load-bearing assumption. The candidate lists it only as a side risk.
  - **Novelty: the stated delta is real but narrow.**
    - Searches found no work that shows a black-box reasoner a predicted arrival-time view. Queries run (all-time, plus since 2025-10-25): "predicted future marks VLM latency robot", "visual prompting moving objects VLM manipulation", "anticipatory visual prompt predicted object position VLM", "predicted future positions overlaid VLM", "VLM dynamic manipulation moving target", "inference delay VLM moving objects", "trajectory prediction visual prompt VLM", "time-delay VLM high-level planner", "set-of-mark robot dynamic", "conveyor VLM", "frontier model robot latency", "stale observation VLM agent", "future state prompting VLM agent", "visual trace prompting", "think while moving VLM", "asynchronous LLM planner real-time". Close-looking hits were no overlap: a driving fast-slow cloud-invocation method, a slow-fast latent bridge for game agents, a trace-conditioned VLA manager.
    - [2409.01652] already has the "act on measurement" half. VLM answers are mark-ID constraint functions "only instantiated when invoked with actual keypoint positions tracked by a specialized 3D tracker", re-solved at ~10 Hz (Sec 3.3–3.4). Run in a world that does not pause, ReKep-style late binding plus an intercept controller already fixes the problem's headline failure (the conveyor grasp landing 20 cm off). The only thing new in C1 is the "decide on prediction" half: arrival-time ghosts that change *which* decision the brain makes.
    - [2606.20458] and [2610.28259]: the phantom-gripper part comes down to anchoring a relative command at the arm pose at arrival instead of at call start. That is ego-only re-anchoring, the case [2606.20458] already handles training-free. Showing the phantom to the brain adds little unless a decision depends on where the arm will be.
    - The baseline list leaves out the most dangerous ablation: query-time marks plus motion trails or velocity arrows plus Δ in text. A frontier brain could do the constant-velocity extrapolation itself from that. [2610.09294] shows prompt-level awareness of world motion already shifts VLM choices. If this baseline matches ghosts, the contribution reduces to a rendering choice.
  - **Mapping: clear and specific.** Brain = controller, world plus executor = plant, call latency = dead time, ghost layer = delay-free model output, arrival-time binding = measurement correction, query stamps = packet numbering. The roles are specified, not just evocative. One caveat: "forecast error cannot move where the decision lands" holds only for targets attached to a tracked rigid entity. Free-space or placement targets defined relative to a ghost inherit the forecast error.
  - **Transfer plausibility: assumption named, but it is the crux.** The candidate names the key assumption: motion over one call is predictable enough to preserve the choice. Under that assumption, the gain over [2409.01652]-style late binding exists only when the right choice depends on the future state: several candidate objects, reachability windows, or which face will be toward the gripper. With a single moving box, late binding alone captures essentially all of the gain. So the measured effect depends on task design. Tasks built to show it will be custom moving-object variants rather than a standard benchmark. This clashes with the panel's "committed effect size on a standard benchmark" bar. [2609.34170]'s non-paused Dynamic Object Manipulation benchmark is the nearest standard testbed, built for VLAs, not frontier brains.
  - **Contribution type: passes.** C1 is a training-free method or system technique (forecast overlay plus late binding), not an analysis or benchmark paper. Feasibility within constraints is plausible: no training, a tracker, a scripted executor with simulator ground-truth poses, and modest API calls. Building kinematic moving-object tasks and an intercept grasp is the main engineering risk for a team new to robotics.
- **Strongest objection in 1 sentence**: The headline failure (a grasp that lands where the box was) is already solved by ReKep-style late binding of mark IDs to tracked poses [2409.01652] once the world keeps moving, so C1's only new mechanism (arrival-time ghosts) helps only with which-decision errors that may be rare outside purpose-built tasks, and it has not been separated from the cheaper alternative of query-time marks plus motion trails plus Δ in text.
- **What a revision must do (for innovator)**:
  - Make the arrival-time view carry something late binding and trail-plus-Δ prompting cannot. Examples: future reachability or feasibility windows rendered per ghost, or several ghosts for multimodal futures so the brain commits to a contingent choice.
  - Name a standard or standard-derived task family where which-decision errors are frequent.
  - Add the trails-plus-Δ baseline as the decisive ablation next to ReKep-style query-time marks.
