# 新 scope：从最新 baseline 出发（2026-10-31）

这份 scope 的推导顺序和之前相反：先找 baseline，再找问题。三个侦察方向分别读了 KV 量化与压缩的 10 个 baseline（A）、已发布模型里的 12 种新注意力结构（B）、长推理解码加速的 10 个 baseline（C），每篇都读了正文，读书笔记在 `papers/`。各方向的详细报告见 `scout_A.md`、`scout_B.md`、`scout_C.md`，本文件是三者的综合。
所有数字都来自读过正文的论文。我自己推算的数字标为"（推算）"。

---

## 1. 三个方向的共同结论

三个方向独立给出了同样的三个判断：

**① 长 CoT 服务的瓶颈是 KV 显存容量，而不只是算力或带宽。**
- A：最强的 2-bit KV 方法里，KVarN 指出公开的服务框架都不支持 2-bit KV；UltraQuant 发现 4-bit 只有在显存不够用时，才比 FP8 更快 [2606.20474]。
- B：稀疏注意力减少的是 KV 读取量，KV 占用"一个字节都没少"。GLM-5.1 处理一个 128K 请求要占 13.09 GB 的 KV，8×H200 在 128K 下只能并发约 15 个请求 [2608.07009]。
- C：所有无损的投机解码方法都要保留完整的 BF16 KV，所以 batch 大小受显存限制。ASPIRE 在 Qwen3-8B 上只能开到 B=30 [2609.17943]；Dustin 加速 9.17×，但它自己承认显存占用没有减少 [2606.24957]。

**② "长生成"是被测得最少的场景。大多数论文测的是长 prompt 加短输出。**
- MagicDec 和 QuantSpec 只生成 90–96 个 token [2408.11049, 2502.10424]。
- DFlash 的 drafter 只在 ≤4K 长度上训练过 [2602.06036]。
- MoBA 在生成阶段换回了全注意力 [2502.13189]。
- TurboQuant 在 prefill 类任务上接近无损，但到了长 CoT 解码，4.6 bit 的效果还不如 2-bit 的 KIVI [2504.19874, 2606.03458]。

**③ token 数少，不等于时间少；准确率不变，也不等于成本不变。**
- KV 量化可能让推理长度变成原来的 5.1 倍。ThinKV 只做思维自适应量化时，吞吐只提高 1.1×，因为输出变长把收益吃掉了 [2510.01290]。
- DEER 把输出缩短了，延迟反而变高 [2604.06787]。
- DeepSeek-V3.2 的推理轨迹比 Gemini-3.0-Pro 更长 [2512.02556]。

所以**评测必须报告"每解出一题的时间、字节和 token"**，而不能只看准确率或单个 token 的延迟。

|---|---|---|---|---|---|
| **S1：长 CoT 解码阶段的 KV 压缩，以每题成本为目标，在显存打满的条件下评测** | 量化让推理变长，最多 5.1×；离线代理在 3 个模型里有 2 个选错 bit 宽；同一种方法在不同论文里结果差异巨大（AIME 56.7 和 0）；长 CoT 的 batch 被 KV 显存限制 | 有。KVarN（vLLM）、PM-KVQ、R-KV、TurboQuant（vLLM PR）、FP8 原生实现 | 中等。KV 量化本身很拥挤，但"长生成 + 每题成本 + 显存打满"这个组合几乎没人测过 | **能**。第一周可以用 fake-quant 和现有代码，不需要写 kernel | **推荐** |
| S2：DSA/CSA 系稀疏注意力的 indexer 开销 | 在 200K 时，indexer 至少占解码时间的约 43%（推算）[2603.12201]；V4-Flash 在 128K 时，indexer 的 FLOPs 约为核心注意力的 6 倍（推算）[2606.19348] | IndexCache、SPIN、MLIPS、HiSparse 都是 2026 年 10 月的 SGLang 或 vLLM 实现 | **高**。V4.1 已经用上了跨层复用，只剩"时间维"和"第一次全扫描"两个方向还没人做 | 难。模型很大（V3.2 671B、V4-Flash 284B），而且必须写 kernel | 适合系统能力强的人，作为备选 |
| S3：长 CoT 投机解码在满 batch 下的系统对比，加上压缩验证 | 训练式 drafter 在并发 32 时加速减半；稀疏自投机则 batch 越大越好；两类方法**从来没有在同一引擎、长 CoT、满 batch 的条件下比较过** | EAGLE-3、DFlash、Vegas、n-gram 都有代码 | 中等 | 能（测量为主） | 可以作为 S1 的第二阶段 |
| S4：混合模型的全注意力层 KV 压缩，以及状态重放 | 在 32K 以上，全注意力 KV 约是状态的 20–80 倍（推算）；近似重放没有误差界 | GateSight、SuffixReplay、DASC、Tail-Replay | **高**。我们之前的 L2 三轮都卡在新颖性上 | 中等 | 暂不推荐 |

## 3. 推荐的 scope：S1

**一句话**：在长思维链的**解码阶段**压缩 KV，让推理模型在**显存打满的真实服务条件下**，"每解出一题"的时间和显存都更少。不能只在准确率上无损，还要不让推理变长。

### 3.1 为什么是它
- **问题真实，有量级**：上面三条共同结论里，有两条直接指向这里。
- **baseline 新、强、能跑**：KVarN（2026-06，有 vLLM 代码）、PM-KVQ（ICLR 2026，有代码）、R-KV（有代码）、TurboQuant（vLLM 社区 PR），第一周就能跑起来。
- **适合新手**：先用 fake-quant 在单卡上做测量和方法原型，等方法确定以后再找组里同学一起写 kernel。
- **连接已有经验**：可以接上你最早想做的"推理"方向，以及师兄说的"KV 量化时机"。

### 3.2 这个 scope 里还开放的方法切入点

**(a) 把轨迹状态作为信号，在线调整 KV 精度。** 一旦出现循环、反思词密集、长度失控这类不健康的迹象，就提升 KV 精度。
- 证据：已有工作测到，KV 量化会让推理变长 [2510.01290, 2606.03458]，低预算淘汰会导致不收敛的循环 [2512.12008]。
- **必须正面区分的近邻工作**：
  - **2606.02011**（2026-06）：针对 2-bit **权重**量化，做循环检测，然后提交答案或用 FP16 从头重跑。
  - **2606.25519**（2026-06）：提出 CTIR 指标，衡量**权重**量化后推理变长的程度，结论是只有 QAT 能同时改善长度和准确率。
  - **ThinKV**：按思维类型静态分配精度。
  - **QEvict**：按累计注意力在不同精度层级之间升降。
  - 本方向的差别在于：作用对象是 **KV**；**不用从头重跑**，而是在线把相关块升精度；触发信号来自轨迹本身。这个差别有多大，第一周就要验证。
- **主要风险**：如果最强的 KV 量化器（KVarN 2.3 bit）本身几乎不让推理变长，这个切入点就不成立。

**(b) 找一个能反映"端到端误差累积"的分配代理指标。**
- 证据：Spend Bytes on Breadth 发现，离线失真曲线在 3 个模型里有 2 个选错了 bit 宽 [2610.05685]；OSCAR 的最优性只在"冻结误差"的假设下成立 [2605.17757]。
- 近邻工作：KVTuner、PM-KVQ、MultiAlloc 都是离线、静态的。KVarN 的 pseudo-decode 只用来诊断，没有用来做分配。
- 需要找一个便宜的信号，能正确预测"哪种 bit/token/层 分配在长生成里最好"。

**(c) 把省下来的显存换成更大的 batch，同时保证输出不偏。**
- 证据：所有无损投机解码都保留完整 KV [2609.17943, 2606.24957, 2601.11580]。
- 近邻工作：QuantSpec（INT4 draft 加 INT8 验证，只测了 bs=1、90 个 token）、VeriCache（压缩的 draft 加完整 KV 验证）。
- 还没有人测过这种 Pareto 曲线：在长 CoT、显存打满的条件下，"压缩 KV 并验证"能换来多少 tokens/s/GPU。
- 这个切入点工程量最大，适合放在第二阶段。

### 3.3 必须比较的 baseline

| 类别 | Baseline | 是否有代码 |
|---|---|---|
| 部署下限 | FP8 KV（vLLM/SGLang 原生）、KIVI-2 | 有 |
| 免校准的 2-bit 解码 | **KVarN** [2606.03458] | 有（vLLM） |
| 校准 / 旋转 INT2 | **OSCAR** [2605.17757]、**OptR** [2608.02691]（侦察 A 漏掉的强 baseline，2026-09）、TurboQuant [2504.19874]，后者要同时跑"边界层保留 BF16"和不保留两种 | OSCAR、OptR 未注明代码；TurboQuant 走 vLLM PR |
| 长 CoT 混合精度 | **PM-KVQ** [2505.18610]、**ThinKV** [2510.01290] | PM-KVQ 有代码；ThinKV 未注明 |
| token 淘汰 | **R-KV** [2505.24133]、DMS [2506.05345]、保住 prompt 的随机淘汰 [2609.03430] | R-KV 有代码 |
| 推理变长的处理 | **2606.02011** 的循环检测加 FP16 回退、2606.25519 的 CTIR 指标 | — |
| 如果做切入点 (c) | QuantSpec [2502.10424]、VeriCache [2605.17613]、EAGLE-3 [2503.01840]、DFlash [2602.06036]、Vegas [2602.07223]、n-gram | EAGLE-3、DFlash、Vegas 有代码 |

**模型**：Qwen3-8B 和 Qwen3-4B-Thinking-2507（多篇论文共用，方便和已发表的数字对比）、R1-Distill-Qwen-14B/32B、gpt-oss-20b（滑窗混合结构，用来证明不只适用于稠密模型）、Qwen3.5-9B（GDN 混合结构，可选）。
**基准**：AIME 2025/2026（avg@16 以上）、MATH-500、GPQA-Diamond、LiveCodeBench。
**指标**：准确率、生成 token 数、撞到长度上限或陷入循环的比例、相同字节下的显存（scale、BF16 窗口、保护层都要计入），以及**每解出一题的墙钟时间**，在 batch 从 1 一直扫到显存打满的范围内测量。

### 3.4 第一周计划（同时也是 kill test）
1. **搭测评框架**：vLLM，加上 KVarN、PM-KVQ、TurboQuant（vLLM PR）、FP8，统一用 Qwen3-8B 和 Qwen3-4B-Thinking-2507，在 AIME25 和 MATH-500 上测 2、3、4 bit。
2. **测三件事**：
   - KV 量化让推理变长了多少（参照 CTIR 的定义）；
   - 卡长度上限和陷入循环的比例；
   - 在显存打满的 batch 下，每解出一题的时间。
3. **顺便复现 QuaRot-INT2 的矛盾**（一篇论文 AIME 56.7，另一篇是 0），弄清是哪个协议细节造成的。
4. **停止条件**：如果最强的 KVarN 在 2–3 bit 下推理只变长 < 10%，并且每题成本已经明显优于 FP8，那么切入点 (a) 就没有空间，转向 (b) 或 (c)。如果变长 ≥ 20%，或者循环比例明显上升，(a) 成立，第二周开始做方法原型。

### 3.5 风险
- KV 量化本身很拥挤，2026 年每个月都有新工作。新颖性必须落在"长生成 + 每题成本 + 显存打满"这个组合上，而不是"又一个量化器"。
- 两篇 6 月的论文已经把"推理变长"这个现象讲清楚了，尽管它们针对的是权重量化。所以本方向不能只停留在"发现这个现象"，必须给出方法。
- OSCAR、OptR、ThinKV 没有注明代码，需要自己复现，存在复现风险。

## 4. 备选：S2（如果组里有人能写 kernel）
**一句话**：DSA 系模型在长生成时，降低 indexer 每个 token 都要做一次 O(L) 扫描的开销，重点是**跨解码步复用**，或者去掉"第一次全扫描"。
- 必须比较的 baseline：IndexCache [2603.12201]、SPIN [2610.09025]、MLIPS/Prism [2610.27438, 2610.22985]、HiSparse [2608.07009]；还要讨论 V4.1-Flash 的 CSA2 [2609.19969]。
- 模型：DeepSeek-V3.2 和 V3.1-Terminus（只有注意力结构不同的一对模型）、V4-Flash。
- 风险：这些都是 2026 年 10 月刚出的工作，竞争最激烈；模型大，工程量重。
